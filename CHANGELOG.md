# Changelog

## 0.4.1 - 2026-11-18

Five more coding agents. `antumbra setup` connected Claude Code alone. It now connects Gemini CLI, Codex, GitHub Copilot CLI, goose and OpenCode as well, each with what Claude Code has: the server's tools, what Antumbra remembers when a session opens, what is recalled for each prompt, and a reminder to store what was learned. Two pieces carry all five: a bridge that takes an agent's MCP connection to the server without the token ever being in the agent's config, and one command that answers any agent's hook with the scripts Claude Code runs. Every one was run against the real tool. All of it is in the CLI, so a server on 0.4.0 needs no upgrade. Read "Before you upgrade" first: setup now connects agents it finds without being asked to.

### Before you upgrade

- **Setup connects every agent it finds** ([#436](https://github.com/albedosehen/antumbra/pull/436)). Run again after upgrading, `antumbra setup` connects Claude Code and each of Gemini CLI, Codex, Copilot CLI, goose and OpenCode whose program is on the PATH or whose config directory is there. To connect only some, name them: `--agent claude`, or `--agent claude,codex`. `--dry-run` says what it would write before it writes anything, and what it writes for each agent is in `docs/integration.md`.
- **Codex runs none of the hooks until you approve them** ([#438](https://github.com/albedosehen/antumbra/pull/438)). Start Codex, type `/hooks`, and approve Antumbra's three. Until then a Codex session has the tools and none of the memory around them, and Codex says nothing about having skipped them. Setup says so when it adds them; it does not approve them for you.
- **A machine with `~/.copilot` is one with Copilot on it** ([#440](https://github.com/albedosehen/antumbra/pull/440)). VS Code's Copilot makes that directory too, and reads the same hooks and MCP servers as Copilot CLI. Setup writes a hooks file of its own there and adds one entry to `mcp-config.json`, with a backup beside it. `--agent` leaves it out.
- **goose's `config.yaml` gains one line** ([#444](https://github.com/albedosehen/antumbra/pull/444)), `GOOSE_MOIM_MESSAGE_FILE`, with a backup, and only when it names no such file. If you keep a file of your own in mind there, it stays yours, and what Antumbra recalls is then left out of goose's context.
- **`antumbra setup check` goes by the agents a setup recorded** ([#436](https://github.com/albedosehen/antumbra/pull/436)). A setup made before 0.4.1 recorded none, and is checked for Claude Code as before. Run setup again to record them.

### Agents

- **Gemini CLI** ([#436](https://github.com/albedosehen/antumbra/pull/436)). An extension of Antumbra's own, `~/.gemini/extensions/antumbra`: the bridge as its MCP server, and hooks on `SessionStart`, `BeforeAgent` and `AfterAgent`. Your `settings.json` is not edited. Gemini CLI connects no MCP server in a folder you have not trusted, and asks before a tool runs; the policy file that allows Antumbra's tools is in the docs, and is the form that worked on 0.68, which the form in Gemini CLI's own documentation did not.
- **Codex** ([#438](https://github.com/albedosehen/antumbra/pull/438)). The bridge is registered with Codex's own `codex mcp add`, and hooks on `SessionStart`, `UserPromptSubmit` and `Stop` are added to `hooks.json` the way setup adds Claude Code's to its settings: adding only, with a backup, never twice. Codex moves a long hook context to a file, so its bootstrap is kept to 7,000 characters.
- **GitHub Copilot CLI** ([#440](https://github.com/albedosehen/antumbra/pull/440)). A hooks file, `~/.copilot/hooks/antumbra.json`, and the bridge as one entry of `mcp-config.json`, put there as text with the rest of the file left byte for byte. Copilot CLI hands its turn's-end hook the session's event log and not the answer, so the answer is read from the end of that log.
- **goose** ([#444](https://github.com/albedosehen/antumbra/pull/444)). A plugin, `~/.agents/plugins/antumbra`: the bridge and three hooks. What a goose hook prints never reaches its model, so the hooks write the file goose keeps in mind instead: the session's bootstrap, and under it what was recalled for the prompt in front of the model.
- **OpenCode, 1.x and 2.x** ([#446](https://github.com/albedosehen/antumbra/pull/446)). OpenCode has no hooks that run a command, and two release lines whose plugins are written differently. Antumbra is one plugin file, `~/.config/opencode/plugins/antumbra.js`, that both lines load. It registers the bridge itself, so `opencode.json` is not edited.

### The CLI

- **`antumbra mcp bridge`: the server's MCP endpoint as a command** ([#434](https://github.com/albedosehen/antumbra/pull/434), [#442](https://github.com/albedosehen/antumbra/pull/442)). Claude Code is given the server's address and a helper that reads the token for each connection. No other agent has such a helper, so each would need the token in its own config file. The bridge is run by the agent and carries its connection to the server set up on this machine, with the token read from its file for each request. A plain `http://` address works where an agent would refuse one. A server that restarted is given a new session without the agent noticing. A handshake that gives no instructions has a paragraph added on when to recall and what to store. It carries both ways of speaking MCP: a session opened with `initialize`, and the 2026-07-28 revision, which opens none and describes each request in its headers.
- **`antumbra hook <agent> <event>`: one implementation of the three touchpoints** ([#436](https://github.com/albedosehen/antumbra/pull/436)). The hook scripts are written to Claude Code's contract. Each other agent has the same three moments and a contract of its own, so its hooks run this command, which hands the script the agent's input in the names the script reads, runs it with the address and names setup recorded, and answers in the shape that agent reads. It never fails the agent.
- **`antumbra setup --agent`** ([#436](https://github.com/albedosehen/antumbra/pull/436)). `--agent gemini`, `--agent claude,codex`, `--agent all`. A name it does not know is refused before any work is done. `setup.json` records the agents connected and this machine's name.

### Hooks

- **Three switches in the scripts, which `antumbra hook` sets** ([#436](https://github.com/albedosehen/antumbra/pull/436), [#438](https://github.com/albedosehen/antumbra/pull/438)). `ANTUMBRA_BRIEF=0` leaves the sovereign-mode block out of the bootstrap, since it is about Claude Code. `ANTUMBRA_CAPTURE_REMINDER=brief` says the turn's-end reminder in a few lines, for an agent that shows it to you as well as to its model. `ANTUMBRA_CONTEXT_LIMIT` keeps the bootstrap under what an agent takes. For Claude Code nothing changes, but the bootstrap's note on what it left out no longer names 10,000 characters.

### Known limits

- **The bridge does not carry what the server sends unasked**, which today is a log line when another session changes a memory.
- **goose keeps one file in mind for the whole machine.** Two goose sessions at once each write it, so a turn may read what the other session's prompt recalled. On Windows goose runs its hooks with `sh`, and needs one on the PATH.
- **`opencode run` on 1.x exits as the turn ends**, before the reminder can be sent. The turn is still reported. In the terminal interface, against `opencode serve`, and on 2.x the reminder arrives.
- **Copilot CLI does not read the bridge's instructions** unless it is told to for a run; its hooks carry what a session needs. Copilot in VS Code reads the same files by VS Code's account, and was not run.
- **A hook costs about three seconds on Windows**, most of it PowerShell starting, as Claude Code's hooks do.
- **Counting skill use and the guidance before a compaction stay Claude Code's alone.**

## 0.4.0 - 2026-11-18

A console a newcomer can use, and a server that does more of its own work. The terminal console is redrawn in the dashboard's palette and words, opens on lists a person can read, says what every key does, and gains what it was missing beside the website: a Services page with the dependency graph and a service's blast radius, a memory's links drawn, an ask that answers for standing experts, and a Training page that shows what the server is teaching. The dashboard draws the dependency graph too. Under both, three things that waited on a command nobody ran now happen by themselves: a proposed behavior is accepted after it has waited, every training is kept as an evaluation, and the agent's rules and skill counts are kept by the hooks. Read "Before you upgrade" first: one of these changes what a server does on its first pass after the upgrade.

### Before you upgrade

- **The server accepts a proposed behavior once it has waited a day** ([#427](https://github.com/albedosehen/antumbra/pull/427)). On its first pass after the upgrade, the node that trains accepts every proposed behavior that can be taught and has been untouched for 24 hours, and trains the scopes they are in. A workspace with a backlog of proposed behaviors will see all of them accepted at once. To keep accepting to yourself, set the workspace's `accept_after_hours` knob to 0 before upgrading (`K` in the console, with an operator's token), or retire the ones you do not want taught. What the server accepted is marked, and `retire_behavior` still drops one.
- **`route` answers with two more keys, and takes `repo`** ([#417](https://github.com/albedosehen/antumbra/pull/417)). `standing` and `taught` are always present, empty for a user who has neither. A client that checks answers against a schema it saved needs the new one.
- **Run `antumbra setup` again for the new hooks** ([#425](https://github.com/albedosehen/antumbra/pull/425)). The session-start hook changed and setup wires two more. `antumbra claude doctor` says when the installed hooks differ from the ones this build carries.
- **`antumbra tui snapshot` refuses a name it does not know** ([#413](https://github.com/albedosehen/antumbra/pull/413)). `--page`, `--layout`, `--focus` and `--overlay` drew something else for an unknown name; they now fail with the names they take. `--layout` defaults to `list`, and the former names (`focused`, `shadows`, `gate`, `loop`, `evals`, `sovereign`) are still taken.

### The console

- **It is drawn in the dashboard's palette** ([#401](https://github.com/albedosehen/antumbra/pull/401)). The console had a palette of its own, with a colour for each kind of thing. It now takes the dashboard's ground, surfaces, inks and one accent from the dashboard's own stylesheet, which a test holds it to. `--theme` (`ANTUMBRA_THEME`) picks `night`, `mist` for a light terminal, or `mono` for one with few colours, and `t` cycles them. A state is a shape and a word, never colour alone, and only a failure is drawn in another colour.
- **One list of keys, which the footer and the help are drawn from** ([#403](https://github.com/albedosehen/antumbra/pull/403)). Keys were read in one place and described in two others, and the three had drifted. The footer now lists the keys of the view in front and `?` lists every key of the page, both generated from the list the keys are read from. `x` acts on what is selected and says what it will do before `y` does it; what an action did, or why nothing happened, is said on a line above the footer. Esc closes a panel and never quits. A halt is asked of the selected run and shown on it, which needed every run's pending halt in the snapshot.
- **It uses the dashboard's words, and says what each page is** ([#405](https://github.com/albedosehen/antumbra/pull/405)). The pages are Population, Memory, Training, Evaluations and Agent; a shadow is a candidate. A sentence under the tabs says what the page in front is, the top bar says which server is read, as whom and whether reads are succeeding, an empty list says why it is empty and what fills it, and the help ends with what each word means.
- **The Population and Memory pages open on a list** ([#407](https://github.com/albedosehen/antumbra/pull/407)). Both opened on an animated graph of unlabelled marks. Population now opens on a table of the experts beside the detail of the one selected, with Tab moving along Experts, Candidates and Boundaries; Memory lists every memory, strongest first within each kind, with Tab moving along the kinds. Finding in a list of thousands works its matches out once a keystroke.
- **The selection stays on its item through a read of the server** ([#409](https://github.com/albedosehen/antumbra/pull/409)). Each list kept its selection as a row number, and a read replaces the lists, so the marked row jumped to another item every few seconds. Every list now finds what was selected again by what it is.
- **The ask says why no expert is routed, and names a standing expert by its scope** ([#411](https://github.com/albedosehen/antumbra/pull/411)). The server's reason for routing to no expert was dropped, and a standing expert was listed by its id, so several read the same once cut to the column. The reason is shown, and a standing expert is named by its repository, or `everywhere`, wherever the console names an expert.
- **A training run is told from the next, and charted with the expert's others** ([#415](https://github.com/albedosehen/antumbra/pull/415)). A standing expert is trained again whenever its behaviors change, and its runs read the same in the candidates' list. Each row now says when it was, a run a later one took the place of reads as replaced, a run kept without the base model's reading says so, and the chart is the expert's pass rate from run to run over the base model's.
- **A Services page: the dependency graph, and what a change to a service reaches** ([#419](https://github.com/albedosehen/antumbra/pull/419)). A dependency claim showed as a line of text among the memories. The sixth page draws the graph, a service before what it depends on, with a line's stroke for the source of the claim, and lists the selected service's blast radius beside it with what says so. Tab turns the walk round and `h` lets it go one hop, three or six. It is worked out from what the console already reads, so it asks the server nothing more.
- **A memory's links, drawn** ([#421](https://github.com/albedosehen/antumbra/pull/421)). `l` on the Memory page drew three rings of unlabelled dots. It now draws the selected memory with what links to it and what it links to, each by how its content starts, and the keys move through the memories that have a link.
- **The Training page shows what the server is teaching** ([#429](https://github.com/albedosehen/antumbra/pull/429)). It showed the loop a person runs and told them to run it. It now opens on the standing experts: each scope with how many of its behaviors are trained, accepted and proposed, when it was last trained, and what the server does next. The Evaluations page names a training and an audit in words, with the base model's reading beside the expert's.

### The dashboard

- **The dependency graph is drawn, and walked one hop, three or six** ([#423](https://github.com/albedosehen/antumbra/pull/423)). The dependencies section was a table. Above it the graph is now drawn, with a picked service filled and what its walk reached outlined; a box picks its service. `depth`, which the server always took, is sent.
- **The route form and the behaviors list say more** ([#417](https://github.com/albedosehen/antumbra/pull/417), [#427](https://github.com/albedosehen/antumbra/pull/427)). The route form shows how close a task is to each standing expert and the nearest of what was taught, and a behavior the server accepted is tagged as accepted after waiting.

### Server

- **`route` says how close a task is to each standing expert, and to what was taught** ([#417](https://github.com/albedosehen/antumbra/pull/417)). A standing expert is never routed to, so a user whose experts are all standing ones was told nothing about any task. `route` now returns each of the caller's standing experts with the task's likeness to what it was taught, whether the task is in its scope, and whether it would answer the task alone, and the three behaviors nearest the task with whether each was learned.
- **The keeper accepts a behavior that has waited** ([#427](https://github.com/albedosehen/antumbra/pull/427)). A proposed behavior waited for its user to accept it, and most are never looked at. On the node that trains, one that can be taught and has waited as long as the workspace's `accept_after_hours` says is accepted for its user and taught in the same pass. `list_behaviors` says which were accepted that way.
- **Every training and every audit is kept as an evaluation** ([#427](https://github.com/albedosehen/antumbra/pull/427)). Evaluations were written only by the generational loop, which runs by hand, so a server that had trained an expert many times showed none. A training, admitted or refused, and each measurement of a served expert on later examples is now a row, with the base model's reading beside the expert's.

### Hooks and setup

- **The agent's rules are kept, and its skills counted, without a command** ([#425](https://github.com/albedosehen/antumbra/pull/425)). The console's Agent page was filled by `antumbra claude remember`, which a person had to run, and by two hooks a person had to paste into their settings. The session-start hook now keeps the rules, detached, in the mode they are for (`ANTUMBRA_REMEMBER=0` turns it off), and `antumbra setup` wires the two hooks that count skill use.

### Dependencies

- **The control server's lockfile is clear of the six lettre advisories of 2026-11-17** ([#432](https://github.com/albedosehen/antumbra/pull/432)). lettre moves from 0.11.23 to 0.11.24, and email-encoding with it. The advisories are in the SMTP client the control server sends sign-in links with when it is built with `smtp`: a forged reply after STARTTLS (RUSTSEC-2026-0560), command injection through a bare LF or CR (0561), a message for an address with a quoted local part going to another address (0563), two panics (0562, 0564) and a reply buffered without bound (0565). The main workspace's lockfile does not hold lettre.

### Known limits

- **The generational loop still runs by hand.** `antumbra train` needs a corpus of tasks with their checks, which nothing in the store supplies. What trains by itself is a standing expert, from behaviors.
- **A declared dependency fades unless it is recorded again.** `antumbra claude dependencies` and the GitHub App record them; no hook does.
- **A terminal under about twenty rows lists only the first of the standing experts** on the Training page, and does not say how many it left out.

## 0.3.1 - 2026-11-17

Experts on more than one machine, and a hardening pass. An expert trained on one machine can be served on another, one with no GPU included: its adapter is sealed when it is admitted, pulled by the server that needs it or read back from copal, and its row and status travel with sync, which a server on an embedded store now runs for itself. Around that, the server, the store, the control server and setup refuse a list of things they used to accept: a short signing secret, a mailer that would log sign-in links, a cleartext workspace address, an oversized document, a share of a compartment that is not yours. Read "Before you upgrade" first: a few of these stop a server that was running from starting.

### Before you upgrade

- **The server needs an HS256 secret of 32 bytes or more** ([#334](https://github.com/albedosehen/antumbra/pull/334)). With a shorter one, or the `.env.example` placeholder, `--http` does not start and `--mint-token` does not sign.
- **The control server needs a mailer** ([#323](https://github.com/albedosehen/antumbra/pull/323)). It no longer falls back to logging sign-in links: configure `SMTP_*`, or set `ANTUMBRA_DEV_MAILER=1` for development.
- **Hosted tokens last 7 days by default, down from 30** ([#375](https://github.com/albedosehen/antumbra/pull/375)), unless `--token-ttl-days` says otherwise.
- **A copal archive over plain `http://` off this machine needs `--copal-allow-http`, and a tenancy named in a header needs `--copal-trust-headers`** ([#366](https://github.com/albedosehen/antumbra/pull/366)). A bare `host:port` off this machine now means `https://`.
- **`antumbra setup hosted` refuses a plain `http://` workspace address that is not this machine's** ([#326](https://github.com/albedosehen/antumbra/pull/326)), unless `--allow-http` is given.
- **The networked server has limits it did not have** ([#379](https://github.com/albedosehen/antumbra/pull/379), [#325](https://github.com/albedosehen/antumbra/pull/325), [#327](https://github.com/albedosehen/antumbra/pull/327)): 16 sessions an identity, a 2-minute request timeout, budgets on the public relic routes, and documents capped at 512 KiB and 1,024 chunks.
- **Upgrade the servers that share a store together** ([#387](https://github.com/albedosehen/antumbra/pull/387), [#396](https://github.com/albedosehen/antumbra/pull/396)). The first upgraded server or CLI to open a store moves experts' rows and their status changes to records of their own; a server from before this release writes them the old way until it is upgraded.
- **An agent older than Claude Code 2.1.163 is not reminded by the capture hook** ([#392](https://github.com/albedosehen/antumbra/pull/392)) unless `ANTUMBRA_CAPTURE_NUDGE=block` is set.

### Experts on a machine without a GPU

- **A build with no GPU backend answers from a quantized base** ([#265](https://github.com/albedosehen/antumbra/pull/265)). The server and the CLI built their engines over the dense base, which on a CPU reads about 6 GB a token: about 1.4 tokens a second on an 8-core laptop, after a three-minute load. `antumbra-mcp --serve-quant` (`ANTUMBRA_SERVE_QUANT`) takes `auto` (the default), `off`, `q8_0` or `q4_k`, and the CLI's `ask` and `serve` follow the build the same way. With no GPU backend `auto` is Q8_0, at about six times the dense base's decode speed; a `cuda` or `metal` build stays dense, and `--serve-quant off` restores the dense base anywhere. The server says at start which backend and base form it serves from.
- **Neither quantized form is the dense base, and the difference is measured** ([#317](https://github.com/albedosehen/antumbra/pull/317)). Over 113 held-out examples of two experts, Q8_0 ranks another token first at 3.6% of positions and Q4_K at 14.4%, and 82 and 79 answers pass their behavior's check against the dense base's 85. Q8_0 is the default because it moves an expert least and decodes within 8% of Q4_K. The live checks that measure this (`quant_drift`, `cpu_serve`, `qmatmul_rows`) time the pass over the prompt and each token after it apart: on an 8-core laptop CPU with one expert, Q4_K reads a prompt at 68.8 tokens a second and decodes at 9.0, and Q8_0 at 60.4 and 8.0. They are ignored unless asked for, and no serving or training path changes.
- **What a quantized base does to an expert is recorded on its card** ([#381](https://github.com/albedosehen/antumbra/pull/381)). A training that admits its expert reads the held-out examples through the model as trained and through the base quantized, and writes the comparison under `drift` on the expert's card: how often another token ranks first, and the mean shift. Q8_0 is measured unless `--behave-drift` (`ANTUMBRA_BEHAVE_DRIFT`) on the server or `--drift` on the CLI names other forms; `off` records none. It is recorded and not acted on: nothing reads it to decide where an expert is served.

### Experts on more than one machine

- **A refused retraining no longer replaces the adapter that is served** ([#357](https://github.com/albedosehen/antumbra/pull/357)). Every training of an expert saved its adapter over the one file the admitted expert was served from, before it was known whether the training would be admitted, so after a restart a refused training's weights were the ones loaded. A training now saves a candidate; admission moves it to a file named for its contents, `<expert id>.<sha256>.safetensors`, and records the sha256 and size on the expert's card. The engine loads the file the expert's row names, so an admitted retraining is served without a restart and a refused one is never served. The keeper removes the file an admitted retraining replaced; the CLI's `behave` leaves it and prints where it is.
- **A server serves an expert trained on another machine** ([#365](https://github.com/albedosehen/antumbra/pull/365)). An expert's weights stay on the machine that trained it, so a second server, such as one with no GPU, had its row and could not answer with it. Told where the training server is, `--expert-source http://trainer:8081` (`ANTUMBRA_EXPERT_SOURCE`), a server pulls the adapter the first time it routes to the expert, checks it against the sha256 and size on the expert's row, keeps it under its own adapter directory and serves it from then on without the training server, across restarts. Both servers run with `--http` and the same `--jwt-secret`: each pull is signed for the user being answered and is good for a minute, and the training server gives an adapter only to its owner, or to anyone for a shared expert. A server that verifies with `--jwt-public-key` says at start that the setting is not in effect. An expert admitted before this release has no sha256 on its card and is not pulled until its next admitted retraining.
- **Each admitted adapter has a second copy in copal** ([#382](https://github.com/albedosehen/antumbra/pull/382)). A server that keeps a copal archive (`--copal-addr`) archives every adapter it admits, in the workspace's copal tenant, and puts the file's id on the expert's card. A server that does not hold an expert's adapter looks on its own disk, then asks its expert source, then the archive, and keeps what it reads only if it is the bytes the expert's row names; the server that trained an expert restores its own file the same way when it is gone. A transfer has its own time limit, `ANTUMBRA_COPAL_TRANSFER_TIMEOUT_SECS` (300).
- **Sync carries an expert's row and its status** ([#387](https://github.com/albedosehen/antumbra/pull/387), [#388](https://github.com/albedosehen/antumbra/pull/388), [#396](https://github.com/albedosehen/antumbra/pull/396)). A machine with its own store, kept in step by `antumbra sync`, got its user's memories and behaviors and never learned an expert had been trained from them. An expert's row and each change of its status are now replicated: a retraining and a delete cross as a newer version of one record, a deleted expert's tombstone is purged with the others after the grace period, and an expert demoted or archived on one store is no longer read as active on another. The adapter is a file and is not carried; the row still names the machine that trained it, so a server that reads the row pulls the adapter. Rows written before this release are moved to records of their own the first time an upgraded server or CLI opens the store, and it logs how many it moved. Servers sharing one store should be upgraded together: a server from before this writes rows the old way, and the next start of an upgraded one moves them.
- **A server on an embedded store syncs without being stopped** ([#394](https://github.com/albedosehen/antumbra/pull/394)). An embedded store has one writer, the server that holds it, so `antumbra sync` could not open it while the server ran and the machine stopped serving to sync. Told a remote, `--sync-remote ws://host:8000/rpc` (`ANTUMBRA_SYNC_REMOTE`) with the remote's root user and password (`--sync-remote-user`, and `--sync-remote-pass` or `--sync-remote-pass-file`) or neither for a remote with no authentication, the server runs the same collector on its own connection every `--sync-interval-secs` (15). It holds the store only to read it and to write a batch of rows, never while it waits on the remote, so requests go on being answered, and a row it pulls is written only if nothing newer was written here meanwhile. A remote that is down is tried again and does not stop the server. The stdio server does not sync and refuses the setting.

### Server

- **On an embedded store, a tool call runs as its own caller** ([#319](https://github.com/albedosehen/antumbra/pull/319)). On an embedded store the networked server shares one connection among every identity and signed it in once per request. A `tools/call` sent to `POST /mcp` runs after that request has been answered, so by the time the tool ran the connection could have been signed in again as another identity, and a call could come back with another user's private rows. The connection is now signed in as the session's identity immediately before each tool runs, and the auth lock is held until the tool returns, so tool calls on an embedded store run one at a time. `/mcp/call` was not affected, and a remote deployment, with one connection per identity, is unchanged.
- **The server refuses an HS256 secret under 32 bytes, or the `.env.example` placeholder** ([#334](https://github.com/albedosehen/antumbra/pull/334)). `--jwt-secret` was used as given, so a short secret, or the placeholder anyone can read out of the repository, verified tokens anyone could mint for any workspace and user. `--http` now refuses to start with such a secret and `--mint-token` refuses to sign with one; the message gives `openssl rand -base64 32`. A server running with a secret under 32 bytes needs a longer one before it will start. RS256 (`--jwt-public-key`) is unaffected.
- **The public relic routes have a budget** ([#325](https://github.com/albedosehen/antumbra/pull/325)). `GET /relic/{slug}/public` needs no token and `GET /relic/{slug}/export` reaches the same lookup without one; every call took the server's auth lock, nothing limited how often a client could ask, and `format=pdf` could spend up to a minute of the renderer's time per request. The public lookup now allows each client 30 requests at once and 120 a minute (300 and 3,000 for everyone together), and printing allows 3 at once and 6 a minute per client (20 and 60 for everyone). A request past its budget gets `429` with `Retry-After` before any work. A printed PDF is kept by slug and version (16 entries, up to 8 MiB each), so a repeat request is answered without a second print, and with one connection per identity the lookup no longer takes the lock. Clients are told apart by peer address: behind a proxy that hides it, every client shares one budget.
- **`ingest_document` refuses a document past 512 KiB or 1,024 chunks, before any work** ([#327](https://github.com/albedosehen/antumbra/pull/327)). Neither a document's size nor its chunk count was bounded, and every chunk is embedded one call at a time, so one call under the 4 MiB body limit could mean about 4,200 serial embedder requests. A document past the cap is now refused with `invalid_params` naming the cap, before anything is archived in copal or embedded, and the CLI's `ingest` refuses it the same way. Relics are unaffected.
- **`share_compartment` and `revoke_compartment` act only on a compartment you own, and report what the store did** ([#331](https://github.com/albedosehen/antumbra/pull/331)). `share_compartment` answered `shared: true` whether or not the store kept the grant, so a refused share looked like one that landed; `revoke_compartment` had the same shape. Both now refuse a compartment that is not the caller's, or that does not exist, with `invalid_params` naming `list_compartments`, and a share to the compartment's owner is refused. After the write each tool reads the grant back and reports `internal_error` when the store refused it.
- **A relic's references to private addresses are made inert before it prints** ([#333](https://github.com/albedosehen/antumbra/pull/333)). The PDF renderer (`--pdf-renderer`) fetches whatever a page references while it prints, and the server relied entirely on the renderer being started with `--chromium-deny-private-ips=true`, as the Compose profile does. Before every print the server now replaces with `about:blank` each `http`, `https`, `ws` or `wss` URL whose host is a private, loopback, link-local, shared-range, unspecified or broadcast address, IPv4 or IPv6, or a name that resolves to one. Public hosts and `data:` URIs are untouched. A name that does not resolve stays, and can add up to two seconds to the print.
- **A merge delivery is taken only with a commit sha** ([#335](https://github.com/albedosehen/antumbra/pull/335)). A `pull_request` webhook delivery whose `merge_commit_sha` is not 7 to 40 hexadecimal digits is acknowledged as ignored, with nothing stored or re-anchored. Before, a value with a multi-byte character in its first twelve bytes could panic the delivery handler and drop the ingest. GitHub always sends forty hex digits, so reaching it took the webhook secret or a hostile API answer.
- **A capability card of the wrong shape no longer stops the keeper's behavior training** ([#336](https://github.com/albedosehen/antumbra/pull/336)). An expert whose `capability_card` was an array, a string or a number, or whose `examples` or `audited` section was one, panicked the standing-behavior training task in the keeper and left the audit un-noted. Such a card is now refused with an error naming the expert and left as it was; a null card or a missing section is filled in. It took a hand-edited or legacy row to hit this.
- **One identity and one connection are bounded in what they may hold open** ([#379](https://github.com/albedosehen/antumbra/pull/379)). The networked server bounded the identities it cached but not the sessions one identity could open, and it had no request timeout and no bound on reading a connection's headers. An identity may now hold 16 sessions: opening another is answered `429` with `Retry-After` and a message naming the bound, until one of its sessions is closed with `DELETE /mcp` or goes idle (5 minutes, as before). A request whose response has not begun within 2 minutes is answered `408`, so a `/mcp/call` tool that runs longer is cut while a `GET /mcp` stream is not, and a connection that has not sent its headers within 30 seconds is closed.
- **A token can be revoked by its id** ([#375](https://github.com/albedosehen/antumbra/pull/375)). A token saved on a lost or shared machine stayed valid until it expired, with no way to end it short of rotating the signing key for every workspace. An operator now runs `antumbra revoke-token` with `--token-file` or `--jti`, and within 30 seconds every server refuses that token with the same `401` an expired one gets; a token minted before ids existed carries no `jti`, and the command refuses it and says so. `antumbra setup check` warns when the saved token has three days or less left.
- **The server trusts the network to copal only when told to** ([#366](https://github.com/albedosehen/antumbra/pull/366)). A bare `host:port` in `--copal-addr` became `http://`; it now becomes `https://` unless it names this machine (`localhost` or a loopback address), and an explicit `http://` to any other address is refused at startup unless `--copal-allow-http` (`ANTUMBRA_COPAL_ALLOW_HTTP`, on the CLI too) says the network between the server and the archive is trusted. The networked server (`--http`) also refuses to start when copal's tenancy names the tenant in a request header, unless `--copal-trust-headers` (`ANTUMBRA_COPAL_TRUST_HEADERS`) says the network is the operator's alone; the message names the keyed modes. The compose stack sets both for its own network, and a stdio server, which serves one identity, is not asked for the second.
- **A refusal from an embedder or a reranker carries the endpoint's words** ([#346](https://github.com/albedosehen/antumbra/pull/346)). A 4xx from either became a bare status and the reason was lost: `embed POST {url} failed: http status: 422`. It now reads `embed POST {url} answered 422: input is too long for the model`. A copal answer that succeeds but is not JSON reads `copal POST {url}: the answer was not JSON: …`, where it read `copal response was not JSON: …`; copal's refusal text is unchanged.
- **The server reads `ANTUMBRA_EMBEDDER_MODEL`** ([#341](https://github.com/albedosehen/antumbra/pull/341)). Only the CLI bound `--embedder-model` to that variable, so a server started with it set ignored it. Both binaries now read it (the default stays `all-MiniLM-L6-v2`), and the CLI's `--help` no longer prints the embedder and copal keys when their variables are set.

### The store

- **A grant in another workspace opens nothing in this one** ([#330](https://github.com/albedosehen/antumbra/pull/330)). The read, write and link rules on `memory`, `memory_edge`, `document_chunk` and `grant` looked up a user's compartments without naming the workspace, so a grant row written in another workspace, for the same user and the same compartment key, opened a private compartment here to that user. Writing such a row took the other workspace's owner view or a compartment there with the same key, so it was hard to reach. Every such lookup now names the workspace, and an existing store picks the rules up on connect.
- **Only a compartment's owner can write its row** ([#328](https://github.com/albedosehen/antumbra/pull/328)). The engine's rule let any member of a workspace update or tombstone another member's compartment row, its `owner` included, and a member who rewrote the owner would read everything in the compartment. No tool offered that write. Create, update and delete now require the caller to be the owner; reads stay workspace-wide, and an existing store picks the rule up on connect.
- **A workspace's embedder key is kept to the owner view** ([#329](https://github.com/albedosehen/antumbra/pull/329)). `embedder_config` holds a hosted workspace's embedder endpoint and its bearer key, and any member's session could read the key and rewrite the endpoint. A member session now neither reads nor writes the row. The server and the operator's CLI use it as the owner and are unchanged, and an existing store picks the rule up on connect. The key is also redacted from debug output, so a log line or a panic message cannot carry it.
- **A member can hard-delete only the memories and edges they can write** ([#351](https://github.com/albedosehen/antumbra/pull/351)). The engine's delete rule on `memory` and `memory_edge` checked the workspace alone, so a member session could hard-delete any memory in its workspace, including one in another member's private compartment that it cannot read. No tool reached it: `forget_memory` soft-deletes, and the hard delete and purge paths run in the owner view. Delete now follows the write rules, and an existing store picks them up on its next connect.
- **The record access method is re-asserted on every schema apply** ([#350](https://github.com/albedosehen/antumbra/pull/350)). Table definitions were already rewritten on connect, but the access method was defined only when absent, so a change to its `SIGNIN` clause or session duration reached new stores only and an existing store silently kept the old definition. It is now overwritten like the tables, so a hardened signin or a shorter session reaches every store on its next connect. Principal rows are untouched, and no Antumbra session ends with the re-assert.
- **Distinct workspace and user pairs keep distinct principal records** ([#368](https://github.com/albedosehen/antumbra/pull/368)). A principal's record key was built by joining the workspace and user ids and then replacing `:`, `/`, `\` and `|`, so two different pairs could become one key; the second pair was never provisioned and could not sign in. Each id is now escaped on its own before the two are joined, so no two pairs share a key. No migration is needed: sign-in reads a principal by its `tenant` and `user` fields, so a pair provisioned before the change keeps working. Hosted ids are generated by the server, so reaching this needed caller-chosen ids.
- **Every binary takes the same database flags** ([#340](https://github.com/albedosehen/antumbra/pull/340)). The CLI, the MCP server and the control server each declared the SurrealDB credential flags themselves, and the copies had drifted. All three now read `ANTUMBRA_DB_URL` for the store's address, where only the control server did. The CLI and the MCP server gain the least-privilege `--db-auth database` login (`ANTUMBRA_DB_AUTH`), which needs both a user and a password, and the password no longer prints in `--help` for the CLI and the control server when `ANTUMBRA_DB_PASS` is set.

### The control server

- **The control server refuses to start without a usable mailer** ([#323](https://github.com/albedosehen/antumbra/pull/323)). With `SMTP_HOST` set but SMTP unusable (a bad `SMTP_PORT`, or a binary built without `--features smtp`), it fell back to the stderr mailer and wrote every sign-in link, a live credential for fifteen minutes, to the container's logs. That is now fatal, with a message naming the cause. The stderr mailer is chosen only by the new `--dev-mailer` flag (`ANTUMBRA_DEV_MAILER`), for development; with neither it nor SMTP, startup fails and says what to set. A Compose stack that relied on the implicit dev mailer must set `ANTUMBRA_DEV_MAILER=1` in `docker/.env` or configure `SMTP_*`.
- **Sign-in link requests have a budget per client and for the whole server** ([#332](https://github.com/albedosehen/antumbra/pull/332)). `/login` and `/signup` send an email to any address by design, and the only brake was a cooldown per address as typed: `A@x`, `a@x` and `a+1@x` were three windows, and nothing bounded one client or the server as a whole. The cooldown now treats an address trimmed, lowercased and without its `+tag` as one. In front of it, each client gets 5 requests at once and 10 a minute, and the server 50 at once and 100 a minute; a request past either gets `429` with `Retry-After: 60` before anything is minted or sent. Clients are told apart by peer address, so behind a proxy that does not forward it they share one budget, and each replica keeps its own windows and budgets.
- **Hosted tokens last a week by default** ([#375](https://github.com/albedosehen/antumbra/pull/375)). `--token-ttl-days` defaults to 7 instead of 30, so a token the control server mints expires after a week unless the flag says otherwise.
- **The control server takes its secrets from files, as the MCP server does** ([#359](https://github.com/albedosehen/antumbra/pull/359)). `--db-pass` and `--magic-secret` were flags or environment variables only, so they showed in process listings and shell history. `--magic-secret-file` (`ANTUMBRA_MAGIC_SECRET_FILE`) and `--db-pass-file` (`ANTUMBRA_DB_PASS_FILE`) read the value from a file and trim it; an empty file is refused, and so is giving both a flag and its file. The CLI takes `--db-pass-file` too, `--magic-secret` no longer prints its environment value in `--help`, and `setup hosted` says in `--help` that `--token` and `--signin-link` are for scripts. The file forms are for deployments that mount secrets; the compose stack keeps its `.env`.
- **An invite code is redeemed once, and an account is created once** ([#367](https://github.com/albedosehen/antumbra/pull/367)). Redeeming read the invite and deleted it in a second statement, so two requests racing on one code could both pass, and the second signup silently overwrote the first account's row. The code is now checked and consumed in one statement: a code that is unknown, expired or already used is refused with "invite code unknown, expired, or already used". A second account for the same login is refused with "an account for this login already exists", and the first stands.

### The CLI and the console

- **`antumbra setup hosted` refuses a plain `http://` workspace address unless it is this machine's** ([#326](https://github.com/albedosehen/antumbra/pull/326)). A plain `http://` address was accepted and the token saved for it, so every hook and MCP connection then sent the bearer in cleartext; a sign-in link's scheme was never checked at all. Now `https://` is accepted anywhere, `http://` only for `localhost` or a loopback address, and `http://` elsewhere needs the new `--allow-http` flag. An address with no scheme is refused regardless. The choice is recorded in `setup.json`, and `setup check` lists a cleartext address under things to fix unless it was accepted. Local setups on a loopback address are unaffected.
- **Day-count flags stop at a century** ([#337](https://github.com/albedosehen/antumbra/pull/337)). `antumbra-control-server mint-invite --ttl-days`, `antumbra verifier measure --ttl-days`, `antumbra claude skills --days` and `antumbra claude reanchor --days` take 0 to 36,500. A value past that, or below zero, is a usage error, where a very large one used to panic with a backtrace. `--ttl-days 0` still mints a non-expiring invite.
- **Setup writes the token file whole, into a directory only its owner can enter** ([#371](https://github.com/albedosehen/antumbra/pull/371)). The file was written in place, so a crash mid-write left a truncated token; its directory was made with the process umask rather than 0700; and on Windows the file inherited the directory's ACL. It is now written to a temporary file beside it with mode 0600, synced and renamed into place, its directory is set to 0700 even when it was already there, and on Windows the file gets an owner-only ACL, with a warning from setup where that cannot be set. `antumbra setup check` reports a token file other users can read as a problem; running setup again rewrites it.
- **The CLI and the console report a refused tool call the same way** ([#342](https://github.com/albedosehen/antumbra/pull/342)). Setup, `antumbra claude` and the console each called the server with a client of their own and refused in their own way, so the console showed "answered 400" where the CLI showed what the server said. All three now show the server's own `error` text, read a `401` or `403` as a refused token, and open every message with the tool's name. `antumbra claude` and the console also send the device header, named from `ANTUMBRA_HOST_ID` when it is set and left off otherwise.
- **`--help` describes the capture flags on every command that takes them** ([#354](https://github.com/albedosehen/antumbra/pull/354)). `memory-import`, `consolidate` and `metabolize` share four capture flags with `teach` (`--rounds` and `--lr` among them), but only `teach` described them; all four commands now carry the same lines. The six `antumbra claude` commands word `--surface` and `--token` one way. No flag name, default, environment variable or constraint changed.

### Hooks

- **The bash hooks hand the token to `curl` on stdin, not on its command line** ([#324](https://github.com/albedosehen/antumbra/pull/324)). `antumbra-prompt-recall.sh`, `antumbra-capture.sh` and `antumbra-session-start.sh` passed the `Authorization` header as an argument, where any other user of a shared machine could read it with `ps` for the life of the request. The token now reaches `curl` as a config line on stdin (`--config -`), and the header the server receives is the same. The PowerShell hooks never had the problem and are unchanged.
- **The capture hook names its sentinel safely, in a directory only this user writes** ([#356](https://github.com/albedosehen/antumbra/pull/356)). The sentinel's path was built from the hook's `session_id` and `hook_event_name` as given and kept in the shared temp directory, where another user could create its name first. Both hooks now cut the two values to letters, digits, `_` and `-`, falling back to `default` and `Stop` when nothing is left. The sentinel lives under `$XDG_RUNTIME_DIR` when the session has one, else under `.antumbra/run` in the user's home directory, created with mode 0700; the PowerShell hook uses `%LOCALAPPDATA%\antumbra\run` on Windows.
- **The PowerShell attribution hook denies what the shell hook denies** ([#347](https://github.com/albedosehen/antumbra/pull/347)). `strip-attribution.ps1` had drifted from `strip-attribution.sh`: it let through the robot emoji forms and the bracketed agent name, and worded its deny reason differently. It now denies both and gives the shell hook's reason. The two hooks are held to one list of sixteen cases, eight denied and eight allowed, which CI runs against each.
- **A turn's end is reminded only when a reminder is due** ([#386](https://github.com/albedosehen/antumbra/pull/386)). `antumbra-capture` stopped the first stop of every turn to ask for memories, so a long job that stops many times while it waits was stopped every time. It now lets a stop through when the transcript holds a `store_memory` or `record_behavior` call since it last looked, or when the session was reminded or saved within `ANTUMBRA_CAPTURE_EVERY_SECS` (600; `0` reminds every turn). Under Windows PowerShell 5.1 the hook could not write its sentinel at all, so every stop was reminded, the one after a reminder included; that is fixed. `antumbra setup` gives the hook ten seconds, up from five; an install made before this keeps five until `antumbra setup` is run again.
- **The reminder is feedback, and a compaction is never blocked** ([#392](https://github.com/albedosehen/antumbra/pull/392)). The hook answered with a block, which Claude Code shows its user as "stop hook reported a problem" each time, and before a compaction the same answer blocked the compaction once a session. At a turn's end the reminder now reaches the agent as feedback that keeps the turn going, with no problem reported; before a compaction the hook blocks nothing and tells the summary to keep what has not been stored, and the turn's end after it is reminded. An agent older than Claude Code 2.1.163 does not read the feedback: set `ANTUMBRA_CAPTURE_NUDGE=block` for the old answer.

### Dependencies

- **Both lockfiles are clear of the open advisories, and CI audits both** ([#322](https://github.com/albedosehen/antumbra/pull/322)). rmcp and rmcp-macros move from 3.1.4 to 3.10.0, which bounds the tool schema cache in the Streamable HTTP transport this server runs (RUSTSEC-2026-0461); ammonia moves to 4.2.5 and quinn-udp to 0.5.16. The control server's own lockfile, which the audit job never scanned, takes ammonia 4.2.5, quinn-udp 0.5.16, quinn-proto 0.11.19, rustls 0.23.46, rustls-webpki 0.103.17 and the fixed webpki-roots and webpki-root-certs releases.

### Docs

- **The documented installers name a release and show how to verify the archive first** ([#364](https://github.com/albedosehen/antumbra/pull/364)). The README, `docs/getting-started.md` and `docs/agent-setup.md` installed from `releases/latest`, so the script a reader ran was whatever the latest release held. Every one-liner now names a release tag, and the documents say what the installer checks: it carries the sha256 of every archive it may download and refuses a mismatch before unpacking. The two guides also show the download, `shasum -a 256 -c`, then `tar` form, for a machine that should check the archive itself before anything runs.
- **`docs/security.md` says what holds, what depends on the deployment, and what the operator sets** ([#363](https://github.com/albedosehen/antumbra/pull/363)). The document stated guarantees the code does not provide: that a token's audience is always required, and that no hand-authored SurrealQL exists. It now says a server started without `--jwt-audience` verifies no audience, so the flag belongs wherever two verifiers share a key, and it names the hand-authored statements and states that every caller-supplied value is bound as a variable. A new section lists what holds only where the operator sets it: the audience, HTTPS in front of the networked server, the PDF renderer's `--chromium-deny-private-ips=true`, the control plane's SMTP settings, and the secret files.

### Internal

- **`unwrap` is denied, and `expect` and `panic` are warned, in every crate's production code and tests** ([#339](https://github.com/albedosehen/antumbra/pull/339), [#360](https://github.com/albedosehen/antumbra/pull/360), [#361](https://github.com/albedosehen/antumbra/pull/361), [#362](https://github.com/albedosehen/antumbra/pull/362), [#369](https://github.com/albedosehen/antumbra/pull/369), [#370](https://github.com/albedosehen/antumbra/pull/370), [#372](https://github.com/albedosehen/antumbra/pull/372), [#374](https://github.com/albedosehen/antumbra/pull/374), [#376](https://github.com/albedosehen/antumbra/pull/376)). The workspace lints now hold a rule that was kept by hand, and CI's `-D warnings` makes all three errors. Every test returns `Result` and uses `?`, so a failing fixture reports its error instead of a panic with a backtrace; no assertion or test name changed.
- **Test fixtures come from one module, and two timing-bound tests wait for what they assert** ([#355](https://github.com/albedosehen/antumbra/pull/355), [#377](https://github.com/albedosehen/antumbra/pull/377)). `antumbra_store::testing`, behind the store's `testing` feature, gives `mem_store`, `members` and `signed_in`, and the MCP server's tests have `McpServer::for_tests`. The two MCP HTTP tests that failed on unrelated pull requests and passed on a rerun now wait, bounded, for the span and the `429` they assert.
- **Flags, HTTP clients and small helpers are written once** ([#340](https://github.com/albedosehen/antumbra/pull/340), [#341](https://github.com/albedosehen/antumbra/pull/341), [#342](https://github.com/albedosehen/antumbra/pull/342), [#343](https://github.com/albedosehen/antumbra/pull/343), [#344](https://github.com/albedosehen/antumbra/pull/344), [#345](https://github.com/albedosehen/antumbra/pull/345), [#346](https://github.com/albedosehen/antumbra/pull/346), [#354](https://github.com/albedosehen/antumbra/pull/354)). The database, embedder and copal flags live in `antumbra_store::args`, `antumbra_embed::args` and `antumbra_copal::args` and are flattened into each binary, and each CLI subcommand's clap struct is handed to its command whole. The new `antumbra-http` crate holds the one client for the tool surface and the one `ureq` transport; `antumbra_auth::unverified` reads a token's unverified claims; `antumbra_core::text` and `antumbra_core::stats` hold the character-boundary cut and the mean; and the train crate has one candle error shape and one factor-restore loop.
- **The store names every table once and has one `put` and one `get_row`** ([#348](https://github.com/albedosehen/antumbra/pull/348), [#352](https://github.com/albedosehen/antumbra/pull/352), [#349](https://github.com/albedosehen/antumbra/pull/349)). `antumbra_store::tables` holds a constant per table, used by the schema, the repositories, sync and the control server's contract, so a renamed table is a compile error everywhere it is used; the repositories upsert and read a row through `Store::put` and `Store::get_row`. The control server's nine contract resources state their shared defaults once, through `read_only` and `listing`.
- **Two tests no longer depend on what runs beside them** ([#390](https://github.com/albedosehen/antumbra/pull/390), [#398](https://github.com/albedosehen/antumbra/pull/398)). Two control-server tests shared `ANTUMBRA_DEV_MAILER` through the process environment and one failed now and then; each now holds the variable to itself and puts back what was there. And the server's telemetry tests read their spans at any number of test threads: at four, which is what CI runs, the first of them got no span.
- **Issues and pull requests have forms, and there is a `CONTRIBUTING.md`** ([#318](https://github.com/albedosehen/antumbra/pull/318)). A new issue is a bug, improvement or feature form with a component dropdown; blank issues are off, and security reports go to a private advisory instead of a public issue. `CONTRIBUTING.md` covers branches and PR titles, the release-branch flow, the fmt, clippy and test expectations, and how a release is cut.
- **`antumbra_boundary::find_scope` returns an error for a failing context that is not a JSON object**, where it used to panic ([#338](https://github.com/albedosehen/antumbra/pull/338)). Its one caller today is a test, so nothing changes for a running server.

### Known limits

- Only a standing expert carries the sha256 of its adapter, so only standing experts are pulled, archived and served on a second machine. One admitted before this release gets its sha256, and its copy in copal, at its next admitted retraining.
- Serving an expert on a second machine is new. The pull and the archive are tested against a source and an archive stood up inside the tests; they have not yet been run between two machines or against a deployed copal. Sync was run against a networked SurrealDB 3.3, experts' rows and status included.
- A sync that signs in as a user, and not as the owner, does not carry experts or their status: only an owner connection writes those tables, and such a pass counts each one as refused.
- An adapter is held whole in memory on both machines while it is pulled, and pulls run one at a time.

### The console

- **A repository's scope is named by the repository in the lists** ([#260](https://github.com/albedosehen/antumbra/pull/260)). A standing expert trained for a repository has the repository's path as its scope, and in a list about forty columns wide that path filled the row before the row said anything else. The lists now name a repository by the last part of its path, and the panels below them still give it whole. A shadow's row is the scope and its reading, `✦ orders-service · 0.68`; a boundary's row leads with the behavior and ends in the scope.

### Dependencies and security

- **candle 0.11** ([#262](https://github.com/albedosehen/antumbra/pull/262)). zip 7.4.0 and its four advisories (RUSTSEC-2026-0367, -0368, -0369 and -0429) leave the build, and tokenizers moves to 0.23 with it. Two things change on the CPU. On AVX-512 VNNI CPUs candle keeps a repacked copy of quantized weights, so serving a Q8_0 or Q4_K base peaks higher (on a 1.5B model, Q8_0 from 3.3 to 4.8 GB and Q4_K from 2.7 to 3.9 GB) while Q8_0 decodes faster. Its thread pools now default to physical cores; `RAYON_NUM_THREADS` or `CANDLE_NUM_THREADS` sets them.
- **The two SurrealDB advisories are carried while SurrealDB 4 is held** ([#262](https://github.com/albedosehen/antumbra/pull/262)). RUSTSEC-2026-0454 (surrealdb-core's reblessive) and RUSTSEC-2026-0452 (surrealkv) are fixed only in SurrealDB 4. That move is ready but held: SurrealDB 4.0.0 fails a member's vector search when a table's read rule holds a subquery, which Antumbra's grant and hive rules do ([surrealdb/surrealdb#7668](https://github.com/surrealdb/surrealdb/issues/7668)). `.cargo/audit.toml` says why neither is reached here, and both entries go with that move.

### Fixes

- **A memory's neighbors are read in id order** ([#262](https://github.com/albedosehen/antumbra/pull/262)). The read is capped at 256 edges, and SurrealDB 4 returns a scan's rows in no fixed order, so a memory with more edges would get a different set on each call.
- **Runtime threads have room for an embedded SurrealDB** ([#262](https://github.com/albedosehen/antumbra/pull/262)). `antumbra`, `antumbra-mcp`, `antumbra-bench` and `antumbra-control-server` give their runtime threads 16 MiB stacks, as SurrealDB asks of an embedded engine, and the bench and control server block on a 256 MiB thread as the CLI and MCP server already did.

### Docs

- **The Windows CUDA 13.3 build changes with candle 0.11** ([#262](https://github.com/albedosehen/antumbra/pull/262)). cudarc now knows CUDA 13.4, so keeping `nvcc` off `PATH` would fall back to 13.4 bindings; keep it on `PATH`, or set `CUDARC_CUDA_VERSION=13030`.

## 0.2.6 - 2026-11-01

Training you can watch, and experts on the CPU. A standing expert's training now shows in the console as a shadow, and what it missed as a boundary, each read by the scope it trained; a node without a GPU can serve experts at a usable speed; and the memory counts from 0.2.5 add up. x86-64 builds now need a CPU with AVX2.

### Training

- **A standing expert's training is a shadow** ([#256](https://github.com/albedosehen/antumbra/pull/256)). The server's keeper writes it as `exploring` while it trains, then `graduated` when the expert is admitted or `pruned` when it is refused or fails, with a reward curve from the base model's held-out pass rate to the trained one's. The console's penumbra had stayed empty on a server, because only the CLI's loop wrote shadows. An expert minted before this gets its shadow once, from its card.
- **What a training missed is a boundary** ([#256](https://github.com/albedosehen/antumbra/pull/256)). Each behavior the expert did not follow becomes an open boundary beside it, holding the rule, the task it missed and its answer, at the share of that behavior's tasks it failed. Open boundaries are recorded, never gating routing. One goes away when an admitted expert learns the behavior or the behavior is no longer taught.
- **A boundary can belong to a user** ([#256](https://github.com/albedosehen/antumbra/pull/256)). One from a behavior holds that user's own rule, so only they read it. Existing boundaries have no owner and stay shared.

### The console

- **A training reads by its scope** ([#259](https://github.com/albedosehen/antumbra/pull/259)). The penumbra listed a standing expert's training by its id, some sixty characters with the scope where the list cut it off; it now reads `✦ code · behaviors · 0.42 → 0.91`, the pass rate from the base model's to the trained expert's, and its panel gives both. Every shadow's row now ends in where its reward went, its status in its glyph and color.
- **An open boundary shows what it was recorded from** ([#259](https://github.com/albedosehen/antumbra/pull/259)): the scope, the task the expert missed and its answer, and whose it is. The inspector showed a boundary's context only when it was actionable, and every boundary a training leaves is open. The gate summary lists only actionable boundaries, the ones that inhibit routing.
- **Prune and graduate leave a training to its keeper** ([#259](https://github.com/albedosehen/antumbra/pull/259)). They set a shadow's status for the generational loop to read back; the keeper settles its own trainings and never does, so on one of its shadows the console declines them and says to freeze the expert instead.

### Serving on the CPU

- **A bf16 expert loads into a CPU model** ([#252](https://github.com/albedosehen/antumbra/pull/252)). Experts are saved in bf16 and every CPU model is held in f32, so serving one, or warm-starting from one, failed on the CPU. Each factor is now cast losslessly as it loads.
- **The base can be served quantized** ([#252](https://github.com/albedosehen/antumbra/pull/252)), as Q8_0 or Q4_K, each projection quantized as its layer loads and never dequantized. Experts stay dense beside it. On an i9-11900H a production expert went from about 1.4 tokens a second over the dense base to 6.4 at Q8_0 and 8.8 at Q4_K, and loading from about 3 minutes to 15 to 41 seconds. A model loaded this way serves only; training keeps its own path.
- **x86-64 builds target x86-64-v3** ([#252](https://github.com/albedosehen/antumbra/pull/252)), so candle's quantized kernels use AVX2 instead of their scalar fallback. The release binaries and images need AVX2, FMA and F16C: Intel since Haswell (2013), AMD since Excavator (2015). ARM builds are unchanged.

### Memory

- **Pass-overs add up** ([#255](https://github.com/albedosehen/antumbra/pull/255)). A memory an agent recalled for itself and then drew on counted as used but not as judged, so `judged - used` undercounted the pass-overs of any memory that also had one. Every use now counts as a judgment.
- **The capture hook names the machine** ([#255](https://github.com/albedosehen/antumbra/pull/255)), as the MCP client does (`X-Antumbra-Host` from `ANTUMBRA_HOST_ID`), so what an agent recalled for itself is judged against the turn that used it. Run `antumbra setup` again, or copy the new `antumbra-capture` over a hand-installed one.

### Docs

- **How Antumbra holds models** ([#257](https://github.com/albedosehen/antumbra/pull/257)). The docs said GGUF and NF4, which the code never used. They now say what it does: a safetensors base from the Hugging Face hub and safetensors experts, served by candle, trained over a bf16 base (or Q4_K in memory with `--quantize-base`).

## 0.2.5 - 2026-10-29

Memories the system keeps itself. Nobody has to reinforce or penalize a memory: the server counts what recall shows, judges at the end of each turn which of those the answer drew on, links a new memory to what it restates, and lets an unused one fade at its network's half-life. An operator steers it with knobs while it runs ([#253](https://github.com/albedosehen/antumbra/pull/253)).

### Memory

- **The system watches how each memory is used.** Recall counts every memory it returns; the prompt hook names its session, and the capture hook reports the end of each turn (`observe_turn`, which no agent is offered). The server asks the relevance head whether the answer drew on each memory the session was shown, or compares embeddings where no head is configured: drawn on counts as used, the rest as passed over. What an agent recalled for itself counts only when the answer drew on it.
- **Strength.** Each memory's strength is its confidence, halved for every half-life since it was last of use and lowered the more often it was passed over. It is read at every recall, never stored. Recall returns it as `strength` and lets it move the order a little after relevance, within each scope.
- **New memories link to what they restate.** `store_memory` links a new memory (`references`) to the existing ones it comes close to, and one close enough counts as that memory recurring. It returns the ids it linked.
- **An agent's own judgment still counts.** `reinforce_memory` and `penalize_memory` are an agent's lever when its work shows a memory right or wrong; the prompt hook now shows each memory's id so it can.
- **The counts live apart from the memory** (`memory_use`), so counting a recall never re-sends a memory to other devices. Each server counts what it sees.
- **`relate_memories` refuses an end that does not exist** instead of storing an edge to nothing.

### The console

- **Knobs (`K`).** The workspace's memory knobs: whether the system governs memories, the half-life of an unused fact, experience, judgment and volatile memory, how sure it must be that an answer drew on a memory, how close a new memory must come to be linked or to count as a restatement, the most links, how much a pass-over weighs, and how far strength moves recall. Anyone sees them; an operator's token turns them, and they apply to the next recall.
- **The Memory page shows strength** beside confidence, how often each memory was recalled, used and passed over, and when it was last of use. It lists each network strongest first and leaves out edges whose end is gone.

### Hooks

- Run `antumbra setup` again to install the new hooks. A hook installed by hand needs the new `antumbra-prompt-recall` and `antumbra-capture` copied over it.

## 0.1.0 - 2026-10-07

The first public release. Antumbra plugs into the coding agent you already use and gives it a memory that carries across sessions and machines, along with where each memory came from. Claude Code is the agent it is tested with; any MCP client can use its tools over stdio or HTTP.

### Setting it up

Install the CLI with the installer for your OS (below), then, with Docker and ollama running, set it up from a clone of this repository, which the local stack is built from:

```sh
git clone https://github.com/albedosehen/antumbra.git
cd antumbra
antumbra setup local
```

Connecting to a hosted workspace needs no clone: `antumbra setup hosted <url> --token-file <file>`. Then `antumbra setup check` confirms every piece. [docs/getting-started.md](https://github.com/albedosehen/antumbra/blob/main/docs/getting-started.md) walks through it, and [docs/agent-setup.md](https://github.com/albedosehen/antumbra/blob/main/docs/agent-setup.md) lets your agent do it for you.

### What's in it

- **One-command setup.** `antumbra setup local` checks Docker and ollama (and, on macOS and Linux, `jq` and `curl`), pulls the embedding model, generates the stack's secrets, starts SurrealDB and the server, mints a token, proves recall works with it, and connects Claude Code: the hooks, the MCP server and the settings, backed up and only added to. Running it again keeps what is already in place.
- **Hooks for Claude Code.** Recall at the start of each session and with each prompt, and a nudge to write back what was verified when a session stops.
- **Memory with provenance.** A memory about code carries the repository, commit and branch it was learned at. Recall scopes to where you are and marks each memory as live, not on HEAD, or orphaned, and a merged branch's memories move to its merge commit.
- **Recall** that fuses dense and full-text search by rank, with an optional cross-encoder rerank whose calibrated floor lets it answer "nothing relevant". Its legs rank keys instead of reading rows, and memory's read rule reads the owner's compartment record directly, one key read per row instead of a subquery ([#196](https://github.com/albedosehen/antumbra/pull/196), [#198](https://github.com/albedosehen/antumbra/pull/198)).
- **Handoffs** between your machines, a **dependency graph** with `blast_radius`, **compartments** you share on purpose, **documents** recalled separately from memory, and **behaviors**: rules you record with a check that has to tell examples from violations.
- **The operator console** (`antumbra-tui`) and a read-only web dashboard at `/dashboard`.
- **Experts (experimental).** Training and serving small LoRA experts needs an NVIDIA GPU and a source build with the `models` feature. The prebuilt binaries are the light, no-GPU build.

### Known limits

- Setup does not start the reranker. Recall works without it but cannot say "nothing relevant", and on a CPU the reranker is too slow to sit in front of every prompt.
- The server advertises all 33 MCP tools. The 17-tool `agent` profile is a server setting (`ANTUMBRA_TOOLS=agent`) that setup does not apply yet.
- Claude Code is the only agent tested so far.
