# Changelog

## 0.5.2 - unreleased

### Before you upgrade

- **The published server image serves experts, and writes to two volumes** ([#574](https://github.com/albedosehen/antumbra/pull/574)). `ghcr.io/albedosehen/antumbra-mcp` is built with the `models` feature, and the stack mounts the named volumes `antumbra-weights` on `/weights` (the Hugging Face cache, `HF_HOME`) and `antumbra-adapters` on `/adapters`; the root stays read-only. Run `antumbra setup local` again to move to the image and create them. A server with no expert to serve never fetches the base; one that has an expert fetches it, about 3 GB, the first time it is asked to answer through one. `--build-arg FEATURES=` builds the light server.

- **A workspace from before roles: make its first call with the operator's token** ([#581](https://github.com/albedosehen/antumbra/pull/581)). 0.5.1 could leave such a workspace with no owner and no way to one (below). With this release a workspace that has no owner is taken by whoever calls it with the server operator's token, so if a 0.5.1 server left yours that way, one call with that token, or opening the Members page signed in with it, puts it right.

- **A coding agent is advertised 21 tools, not 42, once setup is run again** ([#585](https://github.com/albedosehen/antumbra/pull/585)). An agent's connection now asks the server for the `agent` profile. If your agent calls a tool outside it through MCP (`list_memories`, `workspace_stats`, the compartment and sharing tools, `forget_memory`), set `ANTUMBRA_AGENT_TOOLS=all` in its environment, or name what you need: `ANTUMBRA_AGENT_TOOLS=agent,list_memories`. The dashboard and the CLI are not affected, and a server older than 0.5.2 ignores the request and serves everything as before.

- **The `antumbra` command is larger** ([#594](https://github.com/albedosehen/antumbra/pull/594)): about 126 MB on Apple silicon where it was 110 MB, since it now carries the model backend.

### Accounts

- **A followed link is answered with a page** ([#568](https://github.com/albedosehen/antumbra/pull/568), [#570](https://github.com/albedosehen/antumbra/pull/570)). A browser that follows a link from the control plane is told what happened and what to run next, in a page that runs no script, loads nothing and is not kept; a signup's token is shown on it once. A program is still answered with JSON. It was written for 0.5.1 and merged after that release was cut.

### Your data

- **`antumbra export`** ([#589](https://github.com/albedosehen/antumbra/pull/589)). Every memory that is yours on a server, whole, to a file of JSON Lines: its text, kind, confidence, compartment, the machine it was written on, when, and its git anchor. `--from <workspace>` exports what is yours in a workspace the machine joined. The file is its owner's alone to read, since it holds what looks like a secret too.

### Setup

- **An agent whose command is there and does not run is not taken as installed** ([#571](https://github.com/albedosehen/antumbra/pull/571)). `antumbra setup` with no `--agent` connected Codex wherever a `codex` program was on the PATH. Where that program was another tool's wrapper that fails for want of the real one, setup wrote Codex's hooks, could not register the server, recorded Codex among the machine's agents, and `antumbra setup check` then failed on a machine that had passed it. An agent's command now has to answer `--version`; one that does not is said in a line and left out. `antumbra join --connect` leaves such a Codex out too. A machine 0.5.1 left that way is put right by running setup again with `--agent` naming the agents it has.
- **Setup gives an agent the `agent` tool profile** ([#585](https://github.com/albedosehen/antumbra/pull/585)). The profile was a setting of the whole server, which setup could not turn on without taking the dashboard's and the CLI's tools away with it. A connection now asks for it: `X-Antumbra-Tools`, sent by the headers helper setup writes and by `antumbra mcp bridge`, cuts what that connection is advertised and may call down to what a coding session needs. It narrows what a server serves and never widens it.
- **Gemini CLI, goose and OpenCode are given a joined workspace's tools** ([#587](https://github.com/albedosehen/antumbra/pull/587)). `antumbra join --connect` told Claude Code, Codex and Copilot CLI. The other three are connected by setup through a bundle it writes whole, so each is now given a second one, the workspace's own, holding its server and nothing else: `~/.gemini/extensions/antumbra-<workspace>/`, `~/.agents/plugins/antumbra-<workspace>/`, and `plugins/antumbra-<workspace>.js` in OpenCode's config. Only where setup has connected the agent; `--disconnect` and `--leave` remove them.
- **Where a joined machine's new memories go is kept, not only said** ([#591](https://github.com/albedosehen/antumbra/pull/591)). With `antumbra join --write private`, the default, the agent's connection to the workspace now refuses a call that would write something new there and says why; reading and judging go on. `ask` and `workspace` let a write through. It is read for each call, so `--write` reaches an open session. A machine connected before this runs `antumbra join --connect` again to get it.
- **`antumbra setup local --rerank` starts the reranker** ([#593](https://github.com/albedosehen/antumbra/pull/593)). The stack's reranker was a compose profile to start by hand and an address to write into `.env`. Setup now does both when asked, and keeps it on in later runs. Not by default: the model is a few hundred megabytes, takes about two minutes to be ready the first time, and on a CPU adds to every recall. A reranker of your own named in `.env` is kept, and the GPU build already starts one.

### The server

- **A server on an embedded store no longer stops answering an hour after its last request** ([#577](https://github.com/albedosehen/antumbra/pull/577)). `antumbra-mcp --http` with a `mem://` or `surrealkv://` store and no database credentials has one connection, signed in as each request's member and taken back for the server's own work. The engine keeps a session's expiry when the session is left, so an hour after the last request every query on that connection failed with "the session has expired", the server's own work first and then every request (`session initialization failed`), until a restart. An embedded store's sessions now have no end; each request still signs in afresh, which is where a removed member is refused. A server with database credentials, as `antumbra setup local` starts, was not affected.
- **A workspace from before roles can no longer be left with no owner** ([#581](https://github.com/albedosehen/antumbra/pull/581)). On 0.5.1 the first call to such a workspace, a read among them, recorded its caller as a member unless the call carried the operator's token or they were alone in it. With several people and an ordinary token that closed the workspace: nobody could change a role or make a join code, and an operator's new identity became one more member. Now a member's role is recorded only once the workspace has an owner, and a workspace with no owner is taken by whoever holds the operator's token, whatever their own row says.
- **A member can leave** ([#581](https://github.com/albedosehen/antumbra/pull/581)). A member removes themselves through `POST /members/remove`, whatever their role, unless they are the workspace's last owner. `antumbra join --leave` does it from a joined machine and deletes what the machine kept.
- **`GET /healthz`** ([#583](https://github.com/albedosehen/antumbra/pull/583)). The server answers `200 ok` when one cheap read of its store succeeds and `503` when it does not, with no token and naming no workspace. A check that loaded the dashboard's page, which is served from the binary, passed on a server whose store had stopped answering.

### Serving

- **A standard install serves experts on the CPU** ([#572](https://github.com/albedosehen/antumbra/issues/572), [#574](https://github.com/albedosehen/antumbra/pull/574)). The image `antumbra setup local` pulls was built without the model backend, so on a standard install `answer` escalated whatever experts the store held. It is built with `--features models` now, which adds `g++` to the build for the tokenizer's C++ crate; `--build-arg JOBS=8` holds cargo to eight compilers on a host whose memory the model backend's crates fill at one per core. On one laptop (an 8-core i9-11900H with AVX-512, Docker Desktop's VM at 16 GB), the image built in 18 minutes at eight jobs and is 261 MB. Given the `everywhere` standing expert trained on another machine, it answered one task each of three behaviors that expert learned (held out at 1.00, 1.00 and 0.67 against the base's 0.00), and each answer passed its behavior's own check: the base read through Antumbra's AVX-512 kernels from Q6_K, in 1.3 to 1.5 seconds an answer, the container at 2.8 GiB.
- **A first answer waits out neither the base's download nor its load** ([#574](https://github.com/albedosehen/antumbra/pull/574)). On a server that had never fetched its base, the first `answer` through an expert downloaded the 3 GB inside the request and was cut at the two-minute request limit (408), and the first answer once it was fetched loaded and quantized the base inside the request: 62 seconds on that laptop. `Serve::prepare` now looks for the base in the Hugging Face cache without the network. Where it is not there, it is fetched on a thread of its own; once it is, the serving thread is started to load it before any answer asks it to. Until it is loaded, `answer` escalates at once and says which of the two is under way, and a failed fetch or load is said once and started again by the next answer. On that laptop, with an empty weights volume, the first answer escalated in 0.23 seconds and the fetch took five to nine minutes over two runs; with the base already cached, the first answer escalated in 0.46 seconds while the base loaded, in 76 seconds from a cache bind-mounted from Windows, and the answers after it were served in 1.4 and 0.4 seconds.
- **The server says how it serves** ([#574](https://github.com/albedosehen/antumbra/pull/574)). `workspace_stats` returns `serving`: the device the base is read on (`cpu`, `cuda` or `metal`, the device a model would be loaded on and not only the build's backend), the base's form, and on a CPU the kernels a token goes through (`avx-512`, `avx2`, `neon`, or `none` for candle's). It is `null` on a build without the model backend. `antumbra setup check` says it in a line, and says plainly when the server does not serve experts.
- **The image is checked where it is built** ([#574](https://github.com/albedosehen/antumbra/pull/574)). `scripts/image-smoke.sh <image>` starts an image on an in-memory store with a fixed embedder, so no database and no model download, and requires that `workspace_stats` says it serves on the CPU from a quantized base through Antumbra's kernels and that `answer` escalates with no expert. The image workflow runs it after the build of `main`, and on each platform's own runner before a release's version tag names the image, so an image that cannot serve is never the one setup pulls.
- **An Arm CPU writes an x86-64 CPU's answers** ([#524](https://github.com/albedosehen/antumbra/pull/524)). 0.5.1 left this unknown. One round of the bare base's answers on an Apple M4 Pro folds to the marks an x86-64 CPU writes, at all three forms: Q6_K `beacaa5fa0e90d4f`, Q4_K `796bcc447f840113` and Q8_0 `695ed2218c359a16`.
- **The M4 Pro's rates with 0.5.1's NEON kernels in** ([#508](https://github.com/albedosehen/antumbra/pull/508), [#524](https://github.com/albedosehen/antumbra/pull/524)). Single runs, a 1.5B base, no trained expert. Two or three rows sharing a cutting (#508) shows there: at Q6_K one, two and four requests at once decode at 141.1, 227.1 and 329.3 tokens a second between them, where they decoded 137, 151 and 283, so the dip at two is gone. Reading ahead, prompts asked the first time decode at 162.9 where a token a pass decodes 139.1, and asked again at 349.5 where 304. Q4_K, whose kernel already shared between two, moved as well (215.8 where 172.0 the first time, 480.7 where 389 asked again), so not all of Q6_K's gain in reading ahead is #508's. The plain-row kernels (#524) change nothing that can be claimed, timed before them and after: at Q6_K a token decoded at 137.2 where 140.6 with no adapter, 135.8 where 144.7 through a fresh adapter at one expert's rank and 143.8 where 139.9 at a four-expert blend's, and a prompt read at 409.9 where 412.7; at Q4_K 166.2 where 181.1 with no adapter (a later run read 181.7), 174.9 where 177.5, 177.5 where 174.4, and a prompt 561.3 where 578.1.
- **The installed `antumbra` serves experts too** ([#594](https://github.com/albedosehen/antumbra/pull/594)). The command the installers put on a machine was built without the model backend, so `antumbra ask` and `antumbra serve` refused, and said they needed a GPU. The released command is now a `models` build on all five targets: both answer through an expert on the machine's CPU, as the server image does. A GPU backend is still a build from source.

- **An expert fetched between two machines, and served on Arm** ([#594](https://github.com/albedosehen/antumbra/pull/594)). Until now this had run in tests only. A server on an x86-64 machine held a standing expert's adapter; a server built with the model backend on an Apple M4 Pro, on the same database and signing secret and started with `--expert-source`, was asked for an answer. It fetched the adapter (37 MB, the sha256 its card names), loaded the base ahead of the answer, and answered through the expert: 0.2 to 0.4 seconds an answer once loaded, 4.3 GB in memory, from Q6_K through the NEON kernels. The first ask, while the base loaded, escalated with the reason, as it is meant to. The arm64 image, built from this release and run in a container on the same Mac with that adapter in its volume, answered the same: 0.2 to 0.6 seconds an answer, 3.5 GB.

### Measured

- **A coding agent with Antumbra and without it** ([#579](https://github.com/albedosehen/antumbra/pull/579)). Over five sessions that needed conventions given in earlier ones, Claude Code broke a convention it had already been given 3 times in 22 with no memory (1 to 4 over three runs), and not once with Antumbra as setup wires it, nor with the conventions written into its instruction file by hand. Every task passed in every arm. `docs/measured.md` has what was run and what it does not show: one series, one agent, one model.

### Known limits

- **A server with no GPU trains nothing.** It serves the experts a GPU server trained, fetched from that server (`--expert-source`) or read back from the archive. The two servers have to share a database and a signing secret: that is how the expert's row and the right to its adapter reach the second one, and setup does not arrange it.
- **Nothing fetches or loads the base ahead of the first answer that asks for it.** While it downloads, and then loads, every `answer` through an expert escalates and the agent does the task; the load starts with the first answer after the download ends.
- **A serving thread started by an answer served some other way** (an `act` that did not ask `prepare` first) still loads the base inside that answer, as before.
- **On Apple silicon the NEON plain-row kernels have been timed only without a trained expert,** in single runs. With an expert's adapter, and over a long prompt, where the gain should be, they have not been timed.

## 0.5.1 - 2026-11-21

A workspace has members: each with a name and an image, a role, and a way in that an admin opens and a newcomer asks through. On a CPU, an Arm server and a Mac take the rest of a token's steps through NEON, a served answer no longer depends on the operating system a server was built for, and the AVX2 kernels are measured on a CPU that has only them. The `antumbra claude` commands find a set-up machine's server by themselves, and the dashboard gains an Agent page and the writes that are a user's own.

### Before you upgrade

- **A served answer may be worded differently once more, on any machine** ([#528](https://github.com/albedosehen/antumbra/pull/528)). The rotary table is made by one sine and cosine everywhere, and is neither platform's old table: about one entry in a hundred differs by a last bit from the one a Linux build made, and one in a thousand from a Windows build's. Nothing needs setting.
- **An answer served on an Arm server or a Mac may differ for a second reason** ([#524](https://github.com/albedosehen/antumbra/pull/524)): the MLP's gate, attention and an adapter's factors round there as the x86-64 kernels round, where they were plain loops.
- **A workspace's first person is now its owner** ([#523](https://github.com/albedosehen/antumbra/pull/523)). A member from before roles is given one the first time it is asked for: owner where the workspace has none and they are the one who could be (they hold the server operator's token, or they are the only person in it), and member otherwise. Where several people hold an operator's token, the first of them to open the Members page becomes the owner and can make the others owners.
- **The server has 40 tools where it had 38** ([#520](https://github.com/albedosehen/antumbra/pull/520)): `profiles` and `set_profile`, neither in the `agent` profile. The store gains the tables `member_profile`, `join_code` and `join_request`, and a membership record gains a role, when it joined, and whether it was removed ([#523](https://github.com/albedosehen/antumbra/pull/523), [#526](https://github.com/albedosehen/antumbra/pull/526)).
- **The server has 42 tools, and one more table** ([#536](https://github.com/albedosehen/antumbra/pull/536)): `bring_candidates` and `bring_choose`, neither in the `agent` profile, and `memory_choice`, which keeps what a person decided about each of their memories on their own server.
- **A CUDA server reads ahead, and an answer it serves may be worded differently** ([#553](https://github.com/albedosehen/antumbra/pull/553)). `--serve-ahead` is on unless it is turned off, and it now reaches a server that answers from a CUDA GPU. Reading ahead there decodes through passes of sixteen rows, which the GPU rounds otherwise than a pass of one: over one expert's 78 held-out tasks 33 answers were worded differently, and 61 followed their behavior's check where 59 did. `--serve-ahead off` (`ANTUMBRA_SERVE_AHEAD=off` in `docker/.env`) serves as 0.5.0 did, answer for answer. The keeper trains and audits decoding as the server is set, so an expert is best served under the setting it was admitted under, and `antumbra behave` takes `--serve-ahead` for a training run by hand. A CUDA server now also remembers what it wrote while it runs, as a server with no GPU does: tokens of earlier answers and a hash of each prompt, about five megabytes a blend for at most eight blends, none of it on disk.
- **And `signin`** ([#566](https://github.com/albedosehen/antumbra/pull/566)), also on a store a control plane uses: a sign-in between its link being followed and its token collected, kept fifteen minutes.
- **One more table, `account_membership`** ([#558](https://github.com/albedosehen/antumbra/pull/558)), on a store a control plane uses: the workspaces an account is in. A signup writes its first row; an account from before has none and is read as being in the workspace it was made with. Nothing reads it for a decision yet.
- **`--surface` has no default in the `antumbra claude` commands' help** ([#517](https://github.com/albedosehen/antumbra/pull/517)). A shell that sets `ANTUMBRA_URL` and `ANTUMBRA_TOKEN`, or passes both flags, is served as before.

### Serving on a CPU

- **The gate, attention and an adapter's factors through NEON** ([#524](https://github.com/albedosehen/antumbra/pull/524)). Between a token's products an aarch64 CPU did these as plain loops: an exponential called for every value, and running sums that went back to memory at every step. They are kernels in vectors of four, each its AVX-512 twin's steps with a vector of sixteen taken as four, so each gives the value an x86-64 CPU gives, to the bit. No machine runs both to show it, so every set of these kernels is held to one number a kernel, folded from its values over inputs drawn from a seed: AVX-512 and AVX2 give the numbers on a laptop, and NEON gives them on Apple silicon and under an emulator. On GitHub's Apple-silicon runner (an M1, virtual, one thread, the loop and the kernel turn and turn about in one process, six passes) a kernel takes 0.38 to 0.46 of its loop's time for the gate and attention, 0.22 to 0.25 for an adapter's `A` and 0.17 to 0.19 for its `B` over one row, and 0.08 to 0.20 of it over several rows.
- **A served answer does not depend on the operating system** ([#528](https://github.com/albedosehen/antumbra/pull/528)). A Windows build and a Linux build of one tree wrote different answers to the same four prompts in five runs of six (Q6_K, Q4_K and Q8_0, with an expert and without). It was the rotary table, made with each platform's own `sin` and `cos`, which round a last bit their own way. The table is now made with a sine and a cosine written in Rust, on the host whatever device the model is on, and is the same table on Windows, on Linux and on aarch64. The two builds write the same answers in all six runs.
- **The AVX2 kernels, measured on a CPU with AVX2 alone** ([#529](https://github.com/albedosehen/antumbra/pull/529)). On a desktop Intel Core i9-12900KS (AVX2 and AVX-VNNI, no AVX-512) with a 1.5B base, 0.5.0 decodes 47.8 tokens a second from Q6_K, 62.7 from Q4_K and 37.9 from Q8_0, where 0.4.6 through candle's kernels decoded 37.7, 43.4 and 32.5 and llama.cpp (build b12359, its Alder Lake kernels, at its best use of the cores) decodes 43.4, 53.2 and 35.0. With one expert: 46.5, 60.8 and 37.2, where 35.3, 39.7 and 30.7 and, with the expert as a LoRA, 39.5, 46.1 and 32.6. Two long prompts, 2,318 tokens between them, are read at 599 tokens a second from Q6_K and 582 with an expert, where 0.4.6 read them at 287 and 190 and llama.cpp at 463 and 406. A Q6_K token reads 1.19 GB at 57.0 GB a second, 96% of the 59.6 the machine's memory gives, so `auto` stays at Q6_K on such a CPU. Decode is the same from eight threads on the performance cores as from the default sixteen over all sixteen cores, and the answers are the same on every thread count. One Linux binary wrote the same answers on this CPU and on a laptop with AVX-512 VNNI, the kernels' agreement seen on two machines. As a server decodes ([#550](https://github.com/albedosehen/antumbra/pull/550)): one expert's 78 held-out tasks at 59.9 tokens a second reading ahead where 46.2 a token a pass, 71.4 once the reader had answered the tasks the expert was taught, and 378 when the tasks were asked again (a request in 110 ms where 634), every answer the same; eight requests together, 275.9 tokens a second in all from Q6_K and 333.3 from Q4_K. That machine's memory ran at 4000 MT/s, four modules at two to a channel where the kits are rated 5200 for two ([#556](https://github.com/albedosehen/antumbra/pull/556)), so its decode figures are that layout's.

### Serving on a GPU

- **Several tokens a pass on a CUDA GPU** ([#553](https://github.com/albedosehen/antumbra/pull/553)). A GPU decoded a token a pass: nothing carried a guessed row for it. A pass there is mostly the reading of the weights and a few thousand small launches, which its rows share, but the GPU's library rounds a row read among others otherwise than the row read alone, and guesses simply read beside the token in hand rewrote a third of one expert's answers. Among rows of one count the library does compute a row the same way wherever it is and whatever is beside it, to the bit, and a row's attention the same way whatever lies where it may not look. So a model that reads ahead on a CUDA device reads every pass at one shape, sixteen rows over as many positions as its generation may come to, the rest of the width padding, and what is guessed decides nothing: on an RTX 3090 Ti a reader that had answered nothing, a warm one and the warm one asked again wrote the same 78 answers. Through one expert it decoded 128.8 tokens a second cold, 158.9 warm and 1,106 on tasks asked again, where a token a pass decoded 108.1 (a request in 36 ms where 268); long prompts, 173 where 98 and then 1,265. The model asks the device whether it keeps rows apart, with its own weights, before it reads this way.
- **A pass read ahead on a GPU costs a fifth more than a pass of one row, where it cost two fifths** ([#564](https://github.com/albedosehen/antumbra/pull/564)). Little of a wide pass was arithmetic: an adapter's delta was two small products, a scaling and an add for each of 196 projections, and a norm nine launches, at about four microseconds a launch. The adapters of projections that read one input are now joined when a generation begins and multiplied as two products for the group, and a norm's steps up to its first rounding are one kernel: 11.1 ms a pass through an expert where 13.1, and 8.6 where 9.4 bare. With nothing remembered reading ahead had been no faster than a token a pass there (109.5 against 107.6), and slower for the bare base on prompts unlike any before (124 against 141); it is 128.8 against 108.1, and 139 against 142. The answers are where they were: 33 of 78 worded otherwise than a token a pass, where 34. The whole norm in one kernel, rounded once, was tried and left out: 0.8 ms less of a pass, and half again as many answers reworded. Figures and the reasoning are in [Running the trainer](docs/running-the-trainer.md).

### Agents

- **The `antumbra claude` commands find the server a machine was set up for** ([#514](https://github.com/albedosehen/antumbra/pull/514), [#517](https://github.com/albedosehen/antumbra/pull/517)). `antumbra setup` keeps the token in a file and the address in Claude Code's settings, and the six commands that call the server (`dependencies`, `remember`, `auto-mode-env`, `skill-used`, `skills`, `reanchor`) read the token only from `--token` or `ANTUMBRA_TOKEN`. So the two `skill-used` hooks setup wires were refused on every call and counted nothing, without a word, and `antumbra claude skills` in a terminal called this machine's own address. They now find what is not given as the hook scripts do: the flag, then the environment, then what setup recorded, then this machine's own surface, with the token read from its file. The file's token is presented only to the server it is for; a `--surface` that is another server's gets the token it is given and no other. A call turned away with no token to present says so, where it said the token may have expired.

### Members

- **A member's profile** ([#520](https://github.com/albedosehen/antumbra/pull/520)). The name a member goes by and their image, one to a member in a workspace, set from the dashboard's Account page or by `set_profile`. An image is at most 256 KB and is a PNG, a JPEG or a WebP by its first bytes, never an SVG; a member writes only their own.
- **Roles, and a Members page** ([#523](https://github.com/albedosehen/antumbra/pull/523)). Owner, admin and member, a member's standing in one workspace; not the `operator` claim, which is whoever runs the server. Only an owner changes a role, an admin removes members, and a workspace keeps an owner. A removed member's token is refused on every route from their next request. `GET /members` lists them; the page shows each with their image, name, role and when they joined.
- **Asking to join a workspace** ([#526](https://github.com/albedosehen/antumbra/pull/526)). An admin or an owner makes a join code; someone with no token asks with it under a handle (`POST /join/request`), an admin approves or refuses, and the newcomer collects a token once (`POST /join/collect`). `--members-only` (`ANTUMBRA_MEMBERS_ONLY`) refuses a signed token for a pair the workspace does not hold, where it was provisioned. A server that verifies RS256 has no key to sign with and takes no requests.
- **`antumbra join`** ([#531](https://github.com/albedosehen/antumbra/pull/531)). `antumbra join <server> --code <code> --handle <handle>` asks: it makes a secret, keeps it in `~/.antumbra/join.json`, and sends its SHA-256. `antumbra join --status` says how the request stands and, once it is approved, collects the token into `~/.antumbra/workspaces/` beside the machine's own, which is not touched. `--forget` drops a request that is waited on. A plain `http://` address that is not this machine is refused unless `--allow-http`.
- **A joined machine reads the workspace with each prompt** ([#534](https://github.com/albedosehen/antumbra/pull/534)). The prompt hook asks the machine's own store and each workspace `antumbra join` recorded, at most three, at the same time, and gives what a workspace holds under a heading that says it is the team's and not the person's own. Nothing is written to a workspace by it; `ANTUMBRA_RECALL_WORKSPACES=0` asks only the person's own.
- **Choosing what goes to a workspace** ([#536](https://github.com/albedosehen/antumbra/pull/536)). Joining brings nothing. The original stays where it was. `--dry-run` sends nothing and `--to` names the workspace.
- **Sharing a compartment with the whole workspace** ([#540](https://github.com/albedosehen/antumbra/pull/540)). An owner opens the workspace's pool; a member offers a compartment of theirs (`antumbra bring --offer`, or the Knowledge page); an admin or an owner accepts or declines; and what is accepted is listed and recalled by every member until its offerer takes it back. The pool is closed in every existing workspace until its owner opens it.
- **An agent with a workspace's tools, and where what it learns goes** ([#542](https://github.com/albedosehen/antumbra/pull/542)). `antumbra join --connect` registers each joined workspace with Claude Code as an MCP server of its own, which presents the workspace's token and never the machine's (`antumbra mcp bridge --file-token-only`); `--disconnect` takes it out. `antumbra join --write private|workspace|ask` says where new memories go, `private` by default, and the session-start hook tells the agent which workspaces the machine is in and which rule holds.

A self-hosted server is as it was.
- **`antumbra join --email`, and `--control-plane` on the server** ([#563](https://github.com/albedosehen/antumbra/pull/563)). - **Codex and Copilot CLI are given a workspace's tools too** ([#555](https://github.com/albedosehen/antumbra/pull/555)). `antumbra join --connect` registers each joined workspace with every agent on the machine that takes a server by name: Claude Code and Codex by their own commands, Copilot CLI by one entry in its `mcp-config.json`; `--disconnect` takes each back out.

### Known limits

- **No rate has been taken on Apple silicon with the NEON plain-row kernels in.** The timings are a kernel at a time on GitHub's runner. On an M4 Pro a decoded token waits on memory and an expert already cost it nothing, so the gain there should be in a prompt read with an expert on and in attention over a long context.
- **The AVX2 figures are one Intel CPU's,** with four memory modules at two to a channel, which the platform runs at 4000 MT/s where the kits are rated 5200 for two; what it decodes with its memory faster was not measured. No AMD CPU, and no CPU with AVX-512 VNNI and without VBMI, was measured. AVX-VNNI is still not used; llama.cpp uses it there, and the six-bit kernel's count of multiplies would not fall with it.
- **Reading ahead on a GPU was measured on one card,** an RTX 3090 Ti under CUDA 12.6 with the base in bf16. What it rests on is the GPU library's to keep, and a model asks it of its device with a few dozen products, which is a check and not a proof; no other card, and no Metal GPU, has been asked. A wide pass costs a fifth more than a pass of one row there, so reading ahead pays once a pass decides 1.2 tokens; the least any run here decided was 1.17, the bare base on four short prompts unlike any it had answered, at 139 tokens a second where 142. Requests are answered one after another on a GPU.
- **The rotary table was not run on a GPU.** It reaches a CUDA or a Metal device from the host and takes the model's dtype there, as the old one took it there. And whether an aarch64 machine now writes an x86-64 machine's answers is not known: its table and its kernels' values are the same, and no aarch64 machine has answered the prompts.
- **Where a joined machine's new memories go is an instruction to the agent,** not a mechanism: nothing routes a write. Gemini CLI, goose and OpenCode are not given a workspace's tools. What is suggested for sharing is suggested and never sent by itself, and how well it suggests has not been measured on a real store. A member cannot add to a compartment another shared. One join request is waited on at a time, on one machine, the public routes cannot tell their callers apart, so their rate is everyone's together, and a token is collected once: if the answer is lost on the way, the person asks again with a new code.
- **Accounts on a control plane have been run through their tests only:** not against a deployed control plane, a real mailer, or a control server and a public-key server started together over one store. A followed link answers with JSON, not a page, and the dashboard has no sign-in by link.
- **A workspace's settings and the console's actions still ask for the server operator's claim,** not a role. What a removed member wrote stays where it is.
- **Talking to an agent from the dashboard is a note it reads at its next session,** not a conversation. Profiles are not among the tables `antumbra sync` copies.

## 0.5.0 - 2026-11-20

A server with no GPU answers its requests together, on nearly any CPU. Antumbra's own kernels, which the 0.4 releases had only for a CPU with AVX-512 VNNI, now run on Apple silicon and Arm servers through NEON and on every x86-64 CPU through AVX2, and Q6_K is the form served on all of them. The engine answers the requests waiting on it in shared passes, each with its own blend of experts and each as it would be answered alone; it lets go of a request whose caller has gone, gives workspaces turns, and refuses a request past its bound. A pass also carries the tokens guessed to follow and keeps each that is the model's own, so a prompt answered before is answered again in a third of the time. A Mac's Metal build serves from its CPU, where a token is decoded at more than twice the rate. And the dashboard is an application, with pages for the workspace, for the user, and for the policy, which an operator can now change there. `antumbra setup` also follows the agents Unity Gateway starts, and its check says when an organization's policy stops what it wired.

### Before you upgrade

- **A server with no GPU serves from Q6_K through Antumbra's kernels on Apple silicon, on an Arm server and on an x86-64 CPU with AVX2** ([#476](https://github.com/albedosehen/antumbra/pull/476), [#482](https://github.com/albedosehen/antumbra/pull/482), [#497](https://github.com/albedosehen/antumbra/pull/497)). It served from Q8_0 through candle's kernels on all three. What 0.4.3 to 0.4.6 changed on a CPU with AVX-512 arrives there at once: answers are worded differently, a greedy token is the dense head's first, an expert's factors are read at eight bits, and the server holds the head's rows a second time as a sketch, 88 MB for a 1.5B base on Arm and 117 MB on x86-64 without AVX-512 VBMI. `ANTUMBRA_SERVE_QUANT=q8_0` keeps Q8_0. A CPU with AVX-512 VNNI and VBMI serves from what it did.
- **A Metal build serves from the CPU, from Q6_K** ([#483](https://github.com/albedosehen/antumbra/pull/483)), where it served the dense base from the GPU. `--serve-quant off` (`ANTUMBRA_SERVE_QUANT=off`) keeps the dense base on Metal. Training on Metal is untouched, and so is a CUDA build.
- **The server answers waiting requests together, and refuses one past its bound** ([#481](https://github.com/albedosehen/antumbra/pull/481), [#487](https://github.com/albedosehen/antumbra/pull/487), [#489](https://github.com/albedosehen/antumbra/pull/489)). No more than 256 requests wait for the serving engine at once, and no more than 128 of one workspace: one past either is refused at once, as busy, where it would have queued. A request whose caller hangs up or cancels is no longer decoded to its end.
- **A server with no GPU remembers what it wrote, while it runs** ([#492](https://github.com/albedosehen/antumbra/pull/492)): tokens of earlier answers and a hash of each prompt, apart for each blend of experts, about five megabytes a blend for at most eight, in memory only. A request is answered faster where its answer is like an earlier one through the same experts, so a caller who can time answers through those experts can tell that it was. `ANTUMBRA_SERVE_AHEAD=off` (`--serve-ahead off`) decodes a token a pass and remembers nothing. No answer changes for it: every token written is the model's own first token after the text already written.

### Serving on a CPU

The laptop figures are from one laptop CPU (8 cores, AVX-512 VNNI and VBMI) that clocked about half its rating in these sessions, held to its AVX2 kernels where that is said; the Apple figures are from one M4 Pro. All are with a 1.5B base, and figures set beside each other were taken in the same session.

- **Antumbra's kernels in NEON** ([#476](https://github.com/albedosehen/antumbra/pull/476), [#478](https://github.com/albedosehen/antumbra/pull/478)). On aarch64 nothing was tiled, so a served base went through candle's kernels: an expert was read through tensors at every token, a prompt's rows did not share the decode path, and the whole head was read for a token. A CPU with NEON and its dot product, which is every Apple silicon Mac and an Arm server from Neoverse N1, now has the tiles for Q4_K, Q6_K and Q8_0, a prompt's rows sharing a tile's unpacking, and the head's sketch. On the M4 Pro with one expert a base decodes at 136 tokens a second from Q6_K and 177 from Q4_K, where the same machine decoded 72 and 99 through candle's kernels. An expert costs a decoded token nothing there, where it cost a fifth to a third, a prompt is read two to four times as fast, and a base loads at Q4_K in 2.8 seconds where it took 11.4.
- **Two or three rows share one cutting on NEON, in the tiles and in the sketch** ([#508](https://github.com/albedosehen/antumbra/pull/508)). Rows of a Q6_K weight shared a tile's cutting in fours, and what was left of them went a row at a time, each cutting the tile's values out of its bytes again; the head's sketch was cut again for every input. Two rows, or three, are all left over, and two rows together are what two requests answered at once are, and what one request is with a guess riding along after its token. On the M4 Pro at Q6_K two requests decoded 151 tokens a second between them where one alone decoded 137, with no such dip at Q4_K, whose kernel shares between two. The two or three rows left after the fours now go through one cutting, as the fours do, and the sketch's inputs up to four to a cutting. On GitHub's Apple-silicon runner (an M1, virtual, on one thread, the old kernels and the new turn and turn about in one process), two rows of a Q6_K weight take 0.61 of the time they took and three take half, six take 0.80 and seven 0.69; two inputs through the sketch take 0.53 to 0.61 of it, three 0.46, and four or eight 0.38 to 0.40. One row and rows in fours go as they went, the four-row kernel being the one it was, and each row's products are to the bit the ones it gets alone.
- **Antumbra's kernels in AVX2** ([#482](https://github.com/albedosehen/antumbra/pull/482), [#497](https://github.com/albedosehen/antumbra/pull/497)). An x86-64 CPU without AVX-512 VNNI (Intel's from Haswell, its desktop and laptop CPUs since Alder Lake, AMD's before Zen 4) went through candle's kernels as well. It now has every kernel a CPU with AVX-512 has, in vectors half as wide: the tiles, the head's sketch, and the MLP's gate, attention and an adapter's factors. Rows multiplied together cut each tile's values out of their bytes once, products are summed in sixteen bits for as long as they fit, and six-bit tiles are packed for the CPU that multiplies them. Held to its AVX2 kernels with `ANTUMBRA_CPU_KERNELS=avx2`, the laptop decodes at 25.7, 34.0 and 22.6 tokens a second from Q6_K, Q4_K and Q8_0 (24.8, 32.5 and 21.6 with an expert) where its AVX-512 kernels decode at 27.6, 36.2 and 22.1 in the same minutes, and reads a prompt at 98, 125 and 83 where they read it at 145, 151 and 147. A CPU with AVX-512 VNNI and without VBMI (Intel's Cascade Lake) takes its six-bit tiles and its sketch through these kernels, where it had neither.
- **An answer does not depend on whether a CPU has AVX2 or AVX-512** ([#497](https://github.com/albedosehen/antumbra/pull/497)). Each AVX2 kernel sums in whole numbers, takes its AVX-512 twin's float steps and adds across a vector in the twin's order, so it gives the twin's value to the bit. Held to AVX2, the laptop wrote the same answers to the same prompts as it writes with AVX-512, token for token, from all three forms, with an expert and without.
- **Q6_K by default wherever its tiles are** ([#476](https://github.com/albedosehen/antumbra/pull/476), [#497](https://github.com/albedosehen/antumbra/pull/497)). `auto` picked Q6_K only on a CPU with AVX-512 VBMI. It now picks it through NEON and through AVX2 too, where it also decodes faster than Q8_0: 25.7 tokens a second against 22.6 on the laptop held to AVX2.
- **A Metal build serves from the CPU's tiles** ([#483](https://github.com/albedosehen/antumbra/pull/483)). A build with the `metal` feature served the dense base from the GPU, which had never been measured against the CPU. On the M4 Pro the dense base on Metal decodes at 55 tokens a second with an expert, and the CPU's tiles at 135 from Q6_K and 174 from Q4_K; Metal reads a prompt faster than Q6_K does (523 tokens a second against 380) and about as fast as Q4_K. An answer is mostly decoding, and only the CPU path answers requests together, so `auto` in a Metal build now serves as a build with no GPU does.
- **Several tokens a pass** ([#492](https://github.com/albedosehen/antumbra/pull/492), [#497](https://github.com/albedosehen/antumbra/pull/497)). A decoded token reads every weight once, and the same reading carries a further row for a part of what it costs. So a pass carries a request's token in hand and, after it, the tokens guessed to follow; the model gives its own next token after every row, and each guess that is that token is decided without a pass of its own. Rows read together are computed as each would be alone, to the bit, so a wrong guess costs its row and nothing else. The guesses are the token that has followed the same run of one to four tokens before, in the request's own prompt and answer or in what the model wrote for earlier requests through the same experts, and, where the very prompt was answered before, what was written after it then. On the laptop, one expert's 78 held-out tasks at Q6_K, one request at a time, decoded at 33.6 tokens a second where a token a pass decoded 26.8 beside it, on a server that had answered the tasks the expert was taught (28.7 where 25.8 on one that had answered nothing), and at 105.7 where 26.6 when the same tasks were asked again, a whole request in 413 ms where it took 1172. At Q4_K 39.6 where 34.0 and then 109.4; at Q8_0 29.3 where 20.8 and then 105.6; through a blend of three experts 31.7 where 25.3 and then 97.9. Held to its AVX2 kernels, 28.5 where 25.3 at Q6_K and then 77.6. Every answer was the answer a token a pass gave. For scale, llama.cpp (build b12359) on that laptop, with the same expert as a LoRA on a Q6_K file and the same prompts as the very tokens, decoded them at about 18 tokens a second, at 19 with its own n-gram speculation at its defaults, and at 18.7 with its AVX-512 backends taken away. On the M4 Pro, where a further row costs a third of a pass, with no expert and four prompts of 128 tokens each: asked for the first time, one at a time, 156 tokens a second where a token a pass decoded 135 at Q6_K, and 200 where 173 at Q4_K, 508 tokens in about 380 passes; asked again, 304 where 137 and 388 where 180, 127 tokens in 8 passes. In every pair of runs set beside each other, alone or two or four at a time, reading ahead was the faster.
- **Requests answered together each carry their own guesses** ([#492](https://github.com/albedosehen/antumbra/pull/492)), in the passes they share, as far as a pass has rows beside one for every request. Two at a time decoded 46.5 tokens a second where 40.6 and then 112.2; four at a time 60.1 where 55.5 and then 113.1 where 59.8.
- **How many guesses a pass carries is counted, not set** ([#492](https://github.com/albedosehen/antumbra/pull/492)). A further row costs about a tenth of a pass through the laptop's AVX-512 kernels as it was clocked and a fifth through its AVX2 ones, would cost about a fortieth at its rated clock, and costs a third on a machine whose memory outruns its arithmetic. So the server times its passes by their rows and counts how often each kind of guess was right, and a guess rides along while its chance of being right, by the time a token has been taking, is at least the time a further row has been adding. The more requests share a pass, the less a token costs and the surer a guess has to be.
- **Eight rows share one cutting of a six-bit tile, on AVX-512** ([#492](https://github.com/albedosehen/antumbra/pull/492)), where four did: a Q6_K weight's rows take 0.81 to 0.84 of the time at five to seven rows together and 0.87 to 0.97 from eight to thirty-two, on one thread. The head's sketch is cut once for up to eight rows read together.

### The serving engine

- **Requests that wait are answered in shared passes** ([#478](https://github.com/albedosehen/antumbra/pull/478), [#479](https://github.com/albedosehen/antumbra/pull/479), [#480](https://github.com/albedosehen/antumbra/pull/480), [#481](https://github.com/albedosehen/antumbra/pull/481)). The engine took a lock, set the request's blend and generated to the end, so a second request waited for the first. Where a token is read as a plain row, each pass now decodes one token for every request being answered, up to 32: a request that arrives is taken in at the next pass, and each is answered at its own last token. A request's row is turned to its own position, joins its own cache and reads its own blend of experts, and is computed as it would be alone, so its answer is the answer it would get alone; the tests hold that to the bit, across forms and across blends whose answers differ. The engine keeps eight blends at once and gives a blend's place to another only when no request is reading it, so a request never reads factors that changed under it. On the M4 Pro at Q4_K one request decodes at 176 tokens a second and 2, 4, 8 and 16 together at 267, 344, 375 and 383 between them; eight requests of two blends through the engine took 2.75 seconds where one after another took 5.59, a token a pass; reading ahead, with each prompt answered once before, 2.31 seconds where one after another took 3.09. On the laptop at Q6_K, where memory is slower against arithmetic, one request at a time decodes at 26.8 tokens a second, two at a time at 40.6 and four at 55.5. The server's `answer` and the CLI's `serve` are served together with no change of their own. A GPU build, a dense base and a CPU with none of the kernels answer one request at a time, as before.
- **A request no one waits for is let go of at the next pass** ([#487](https://github.com/albedosehen/antumbra/pull/487)). A request whose caller hung up or timed out kept taking tokens to its end, holding a place in every pass and its blend's slot for an answer nobody read. The engine now drops a waiting request whose caller has gone without reading it, and frees the place and the slot of one being answered. Over MCP, `answer` follows the request's cancellation, which a client's `notifications/cancelled` and a session's close both raise; over REST the call is dropped when the connection is.
- **Workspaces take turns, and the wait is bounded** ([#487](https://github.com/albedosehen/antumbra/pull/487), [#489](https://github.com/albedosehen/antumbra/pull/489)). Requests were taken first come, first taken, so one workspace's burst was answered to its end before another's single request was taken in, and nothing bounded how many waited. A request's turn is now how many of its own workspace's requests are ahead of it, being answered or waiting, and the lower turn is taken in first; within a workspace the order is the order asked. No more than 256 requests wait at once and no workspace holds more than half of those places: one past the bound is refused with "the serving engine is busy", and a workspace's 129th with how many of its requests already wait.

### Known limits

- **A GPU, a dense base and a CPU with none of the kernels answer one request at a time and a token a pass,** as before. A temperature, a repetition penalty or an n-gram block also decodes a token a pass, since a guess is checked against the head's first token.
- **Requests answered together are bound by arithmetic.** Only the reading of the weights is shared, and each row is still multiplied: the M4 Pro decodes a little under twice as much with eight or more at once as with one and no more past that, and the laptop twice as much with four.
- **Turns are counted in requests, not tokens,** so a workspace whose answers are long takes more of each pass's time than one whose answers are short. A caller that names no workspace, the CLI among them, shares one turn with every other that names none. Two workspaces asking a deployed server at once was not run; what is tested is the order the engine takes requests in.
- **A caller is noticed gone between passes,** so a prompt already being read is read to its end.
- **What reading ahead gains depends on what the server has seen.** One that has answered nothing guesses only from the request itself and from its own first answers; the memory is not kept across a restart, is not filled from an expert's taught examples when the expert is loaded, and is one process's. A prompt that was just answered is still read again before its answer is confirmed sixteen tokens a pass, so a repeated request takes about a third of the time, not a sixteenth.
- **The AVX2 figures are from a CPU with AVX-512 held to its AVX2 kernels.** No CPU with AVX2 alone was measured, nor one with AVX-512 VNNI and without VBMI. Through AVX2 a prompt is read at 56 to 83% of the AVX-512 rate and a row carried ahead costs half again as much. AVX-VNNI, which Intel's CPUs since Alder Lake have, is not used.
- **The Apple figures are from one M4 Pro.** Its efficiency cores hurt: fourteen threads decoded at about 130 tokens a second where the ten performance cores decoded at 198. On NEON the MLP's gate and attention are still plain loops. Two or three rows sharing a cutting there was timed a kernel at a time on GitHub's Apple-silicon runner and checked for its values under an emulator; what it does to the M4 Pro's figures for two requests at once, and for reading ahead, was not run.
- **A request with a very long prompt and a short answer is the case Metal wins** against Q6_K on the CPU; `--serve-quant off` is the way to it. A Mac with a faster GPU against its CPU was not measured.
- **The dashboard cannot mint a token or manage members,** and of the console's actions only the policy is there. Two operators saving the policy at once: the later save wins. The theme before the first frame was checked in Chromium only.
- **What setup does for Unity Gateway follows its source, and was not run against a workspace.** It is what `ug`'s source and README said on 2026-11-20, run in a home laid out as `ug` leaves one. Kilo, Pi and Antigravity, which `ug` also starts, are not connected. A relayed `ug claude` launch is told by what `ug` wrote for it, which a later `ug` may write differently, and it still has to be started with the settings file by hand. Codex's `requirements.toml` is read a line at a time for three keys, so one written as an inline table is missed.

## 0.4.6 - 2026-11-19

A token decoded on a CPU no longer reads the whole output head to find its largest logit, and an expert's factors are read at eight bits. A 1.5B base decodes 7 to 10% more tokens a second at every form, and a blend of three experts 3% more on top.

### Before you upgrade

- **A served answer may be worded differently once more, on a CPU with AVX-512 VNNI and VBMI** ([#469](https://github.com/albedosehen/antumbra/pull/469)). A greedy token is now the dense head's first for the hidden row the head is given, where it was the quantized head's: another token at one or two positions in a hundred. Nothing needs setting.
- **An answer served over an expert may be worded differently again, on a CPU with AVX-512 VNNI** ([#470](https://github.com/albedosehen/antumbra/pull/470)): the expert's factors are read at eight bits where they were read at half precision.
- **A server whose CPU has AVX-512 VNNI and VBMI holds 88 MB more** for a 1.5B base ([#469](https://github.com/albedosehen/antumbra/pull/469)): the head's rows a second time, as a sketch.

### Serving on a CPU

- **A greedy token is found through a sketch of the head** ([#469](https://github.com/albedosehen/antumbra/pull/469)). The head has a row for every token, and a decoded token read all of it, 191 MB at Q6_K and 248 MB at Q8_0 for a 1.5B base, to find the one row with the largest product. The rows are now also held as a sketch at three bits a value, 88 MB. A token's products with the sketch pick out the rows that could still be first, about forty of 151,936 at the median, and those are multiplied from the dense rows the embedding table keeps. Over two experts' 5,021 held-out positions the token was the dense head's first at every one, where the quantized head's first was another token at 74. On one laptop CPU a 1.5B base with no expert decodes 23.5 tokens a second at Q8_0 where it decoded 21.4, 29.9 where 27.9 at Q6_K, and 38.7 where 36.1 at Q4_K; with an expert on, 21.7 where 20.7, 28.8 where 26.4 and 37.3 where 34.5. Of the two experts' 113 held-out tasks, 79, 82 and 79 answers follow their behavior over Q8_0, Q6_K and Q4_K, where 80, 82 and 77 did.
- **An expert's factors are read at eight bits** ([#470](https://github.com/albedosehen/antumbra/pull/470)). An adapter is read whole at every token beside the base, 37 MB for one expert and 111 MB for three at half precision. The copy a CPU decodes through now holds each rank's row of `A` and column of `B` as whole numbers of 127ths of its largest value. One expert's log-probabilities over 2078 held-out positions, read a token at a time, shift from the dense base's by 0.103, 0.141 and 0.421 nats on average over Q8_0, Q6_K and Q4_K, where at half precision they shifted by 0.099, 0.146 and 0.418: the order a float sum is added in moves the same reading by as much. A blend of three experts decodes 28.2 tokens a second at Q6_K where it decoded 27.4, and setting it takes 29 ms of packing where it took 41.

### Known limits

- **The sketch picks its rows by a margin, not by a proof.** A row is read whole when its sketched product comes within twelve of its typical errors of the best product found. The furthest any first token's product was seen above its sketched one is 5.4 of them; a row further off than twelve would be passed over, and the token would be the best of the rows that were read.
- **Only a greedy token with nothing applied to the logits is found this way.** A temperature, a repetition penalty or an n-gram block reads the whole head as before, and so does the drift measurement, whose count of changed first-ranked tokens is the whole quantized head's.
- **The sketch is where the six-bit tiles are:** a CPU with AVX-512 VNNI and without VBMI (Intel's Cascade Lake), and any CPU without AVX-512 VNNI, reads the whole head as before.
- **Eight-bit factors buy less than their bytes.** One expert decodes as it did (29.0 tokens a second at Q6_K); the gain is a blend of several. Rounded to four bits the factors do cost an expert (a mean shift of 0.125 nats at Q8_0 where 0.098), so eight is where it stays.
- **The drift on an expert's card is measured with the factors as trained,** on a GPU or a CPU.

## 0.4.5 - 2026-11-19

The server answers what admission verified. Until now it decoded with two penalties that admission never used, and they rewrote answers: a type or a name written twice could come back misspelled the second time. And a server with no GPU now serves from Q6_K by default where that is the faster form.

### Before you upgrade

- **Every served answer may be worded differently once, on a GPU and on a CPU** ([#466](https://github.com/albedosehen/antumbra/pull/466)). It is now the answer admission read. Nothing needs setting.
- **A server with no GPU serves from Q6_K where its CPU has AVX-512 VNNI and VBMI** ([#467](https://github.com/albedosehen/antumbra/pull/467)), where it served from Q8_0: about a third more tokens a second, and answers worded differently again. `ANTUMBRA_SERVE_QUANT=q8_0` keeps Q8_0. On any other CPU, and on a GPU, nothing changes.
- **A training server measures an admitted expert's drift on two forms** ([#467](https://github.com/albedosehen/antumbra/pull/467)), Q8_0 and Q6_K, where it measured one: one more load of the base for each admitted training. `ANTUMBRA_BEHAVE_DRIFT=q8_0` keeps it to one.

### Server

- **The server decodes as admission does** ([#466](https://github.com/albedosehen/antumbra/pull/466)). `ask`, `serve` and `answer` applied a repetition penalty of 1.2 and a block on repeated 3-grams; admission, the audits and the drift measurement applied neither. A block on 3-grams cannot let a name of three tokens be written twice: asked for a function that adds two `i64` values, an expert answered `fn add(a: i64, b: i32) -> i6 { a + b as i6 }`, and without the block `fn add(a: i64, b: i64) -> i64 { a + b }`. Over that expert's 78 held-out tasks the same number of answers followed their behavior either way (57 and 58), and only 14 came out worded as admission had read them: the block misspelled names the second time they were said and changed numbers, and the penalty alone reworded four answers in five. Both are now off in serving, as they are in admission, and stay in `RaftConfig` for a caller that wants them.
- **A generation that runs into a loop ends there** ([#466](https://github.com/albedosehen/antumbra/pull/466)). The penalties were turned on for an expert that repeated itself without end. A loop is one block of up to 64 tokens, three or more times running, over 32 tokens or more; the check changes no token, so it cannot rewrite an answer, and admission ends a loop where serving does. A loop used to run on to the token limit.

### Serving on a CPU

- **Q6_K by default where it is the faster form** ([#467](https://github.com/albedosehen/antumbra/pull/467)). On a CPU that multiplies six-bit tiles a base at Q6_K decodes at 28.6 tokens a second where Q8_0 decodes at 22.1 (one laptop CPU, a 1.5B base), and `auto` now picks it there. Measured on two experts before it was made the default: Q6_K shifts an expert's log-probabilities from the dense base's by 0.144 and 0.120 nats on average where Q8_0 shifts them by 0.098 and 0.086 (Q4_K: 0.413 and 0.365), and of the two experts' 113 held-out tasks 82 answers followed their behavior over Q6_K and 80 over Q8_0 (Q4_K: 77).

### Known limits

- **A loop is ended after 32 tokens of it at the earliest,** and what it had repeated by then stays in the answer.
- **Thirty-two tokens of one block repeated are taken for a loop whatever they are:** a list of sixteen equal values written out in full ends there.
- **Q6_K is the default only where its tiles are:** a CPU with AVX-512 VNNI and without VBMI (Intel's Cascade Lake), and any CPU without AVX-512 VNNI, serve from Q8_0 as before.

## 0.4.4 - 2026-11-19

Serving on a CPU, measured on the model the server actually holds. A request with one expert decodes about a third faster at Q4_K than under 0.4.3, its prompt is read at two to three times the speed, and a blend is set in an eighth of the time. Q6_K joins Q8_0 and Q4_K as a form to serve a base in. A server with a GPU serves as it did.

### Before you upgrade

- **An expert served on a CPU can word a long answer as 0.4.3 did not** ([#463](https://github.com/albedosehen/antumbra/pull/463)). Answers are the same on every run of one build. But a prompt is now read by the arithmetic a decoded token is read by, in another order than before, and the values in between are held in eight bits: within a few layers the two readings are apart by what that rounding is worth, and where two tokens were close the other one can come first. The two are equally far from the dense base. Over one expert's 2078 held-out positions the mean shift in log-probability is 0.098 nats read either way at Q8_0, and 0.41 and 0.42 at Q4_K. Answers on a GPU are untouched.
- **`q6_k` is a new value of `--serve-quant` and `--behave-drift`, and `auto` is Q8_0 as before** ([#464](https://github.com/albedosehen/antumbra/pull/464)). Nothing is served or measured differently unless you set it.

### Serving on a CPU

All figures are from one laptop CPU (8 cores, AVX-512 VNNI) with a 1.5B base, 0.4.3 and this release in runs minutes apart, llama.cpp b12359 at its best thread count beside them.

- **A prompt is read through the kernels a decoded token is read through** ([#463](https://github.com/albedosehen/antumbra/pull/463)). Its rows go through the plain-row step up to 32 at once: a weight is read from memory once for all of them, and each row is computed exactly as it would be alone, so a prompt read at once and its tokens read one at a time give the same logits to the bit. A prompt of 24 tokens is read at 165 tokens a second at Q4_K where 0.4.3 read it at 107, and at 155 at Q8_0 where it read 84; with an expert on, at 153 and 150 where it read 72 and 62. llama.cpp reads it at about 100 and 78.
- **An expert costs a decoded token what its own bytes cost** ([#463](https://github.com/albedosehen/antumbra/pull/463)). Its factors are read at half precision, which holds what a bf16-trained expert holds, and laid out so a vector holds sixteen results and nothing is summed across it. And the ranks that add nothing are no longer read: the server holds a model with room for three experts, and a request with one expert read three experts' bytes at every token, two of them zeros. On that model a request with one expert decodes at 35.0 tokens a second at Q4_K where it decoded at 27.0, and with three at 34.4 where it decoded at 27.9; at Q8_0, 20.8 and 21.3 where it decoded at 18.9 and 17.7. On a model at the trained rank an expert decodes at 36.3 against llama.cpp's 23.3 with the same adapter at Q4_K, and 21.4 against 18.1 at Q8_0.
- **A blend is set in an eighth of the time** ([#463](https://github.com/albedosehen/antumbra/pull/463)). A request whose blend is not the resident one waited while every factor went through five tensors on one thread: 404 ms for one expert and 819 ms for three. Each factor now goes from its file's bytes straight into the model, on every core, with the values the tensors gave to the bit: 50 ms and 101 ms. Through the engine, a request that changes the blend is answered in 1.2 s at Q4_K where it took 2.6 s, and in 2.0 s at Q8_0 where it took 2.8 s.
- **Q6_K: a third form, between the two** ([#464](https://github.com/albedosehen/antumbra/pull/464)). `--serve-quant q6_k` (`ANTUMBRA_SERVE_QUANT`) serves a base with body and head at six bits, about 1.27 GB to read a token where Q8_0 reads 1.64 and Q4_K 0.95. It decodes at 28.6 tokens a second where Q8_0 decodes at 22.1 and Q4_K at 37.9; llama.cpp on a Q6_K file of the same base decodes at 25.1. Over one expert's 2078 held-out positions its log-probabilities shift from the dense base's by 0.145 nats on average, where Q8_0's shift by 0.098 and Q4_K's by 0.413. The default is unchanged.
- **Read an expert's drift by its mean shift** ([#464](https://github.com/albedosehen/antumbra/pull/464)). A card's count of positions that rank another token first moves by ten or twenty in two thousand with nothing but the order a sum is added in: one expert on one Q8_0 base changed 69 positions read as a batch and 90 read a token at a time, at the same mean shift. `docs/running-the-trainer.md` says so beside what a card records.

### Known limits

- **All of this needs AVX-512 VNNI,** as decoding through Antumbra's own kernels did in 0.4.3: without it a prompt and an adapter go through candle as before. Setting a blend is faster on any CPU. Six-bit tiles also need AVX-512 VBMI; a CPU with VNNI and without it multiplies a Q6_K base through candle's kernels.
- **The thread settings 0.4.3's notes named for Linux are no longer needed on a CPU with AVX-512 VNNI.** With the settings as they come, a prompt with an expert is read at 152 tokens a second where 0.4.3 read it at 28. Without AVX-512 VNNI the prompt pass still goes through tensors and `RAYON_NUM_THREADS=1` with `CANDLE_NUM_THREADS` at the core count still helps.
- **An expert still costs a token its bytes:** 37 MB for one expert and 111 MB for three, beside the 0.95 GB a Q4_K base reads. With three experts that is a tenth of the decode rate.
- **The laptop these figures are from ran below its full clock.** That weighs on reading a prompt, which is bound by arithmetic, more than on decoding, which is bound by how fast memory is read.

Two fixes to what 0.4.2 left a training server doing, a knob that pauses that training, decoding on a CPU at two to three times the speed, and a setup that leaves alone an agent that is not installed. Admission asked only that a new expert was not worse than the base model. ### Serving on a CPU

- **A decoded token costs about half what it did** ([#456](https://github.com/albedosehen/antumbra/pull/456)). A profile of the decode step found the whole KV cache copied in every layer for every token, attention and an adapter's products run a row at a time on one thread, and an exponential taken for every value of the MLP's gate on one thread. On one laptop CPU with a 1.5B base at Q4_K, decode goes from 11.8 to 21.5 tokens a second with no expert and from 10.1 to 18.3 with one; at Q8_0, from 10.5 to 17.0 and from 8.8 to 14.8. Answers are unchanged, and so is the time to read a prompt. Training and every GPU path are as they were.
- **On a CPU with AVX-512 VNNI a decoded token is read through Antumbra's own kernels, at the rate memory can be read** ([#462](https://github.com/albedosehen/antumbra/pull/462)). Three things stood between a decoded token and that rate. candle's quantized tiles keep a Q4_K weight's scales as f32, a third more bytes than the weight, and a token is bound by how fast its weights are read: Antumbra now tiles a served base itself, at the size of the plain blocks. On the same laptop CPU and 1.5B base as the entry above, decode goes from 21.5 to 36.7 tokens a second at Q4_K with no expert and from 18.3 to 31.5 with one, and at Q8_0 from 17.0 to 21.8 and from 14.8 to 19.9. At Q8_0 a token reads 1.6 GB and that is now nearly all its cost. Reading a prompt goes from 94 to about 110 tokens a second at Q4_K. For scale, llama.cpp (build b12359) on that laptop at its best thread count decodes the same base at 30.4 tokens a second at Q4_K_M and 21.3 at Q8_0, and with the same expert as a LoRA at 23.7 and 17.6. A decoded token's values no longer depend on which thread did which part, so a greedy answer is the same on every run and on any number of threads. Other CPUs, a prompt's rows, training and every GPU path compute as they did.
- **Loading a base to serve takes a third of the time** ([#462](https://github.com/albedosehen/antumbra/pull/462)). Each weight is quantized a run of rows at a time on every core: 20 seconds for a 1.5B base at Q4_K on that laptop, where it took over a minute on one.

### CLI

- **Setup leaves alone an agent that left only its config directory** ([#460](https://github.com/albedosehen/antumbra/pull/460)). An agent is found when its program is on the PATH, or when its config directory holds its own config file. An agent that was removed leaves its directory behind, and setup used to connect it. Setup's last lines now say which agents it connected because it found them, and that `--agent` chooses them.
- **`antumbra setup check` does not fail on a Codex that is not installed** ([#460](https://github.com/albedosehen/antumbra/pull/460)). A server that could not be registered because `codex` is not on the PATH is said with what to install, and the check passes. It used to fail with "run setup again", which could not help.

### The console

- **The Training page says when training is paused, and shows a full scope as in step** ([#457](https://github.com/albedosehen/antumbra/pull/457), [#455](https://github.com/albedosehen/antumbra/pull/455)). A scope whose expert holds exactly its set no longer reads as waiting to be trained.

### Known limits

- **A scope with many behaviors waiting is still trained once a pass until each has had its turn,** and more of those trainings now change nothing: one that misses a behavior the expert held is discarded. `standing_training` pauses them. A scope taught by more than one expert is what lets it grow past this.
- **Decoding through Antumbra's own kernels needs AVX-512 VNNI.** Intel's Ice Lake and Tiger Lake laptop CPUs and its Xeons from Cascade Lake have it, as do AMD's CPUs from Zen 4; Intel's desktop and laptop CPUs since Alder Lake do not. The six-bit head's tiles also need AVX-512 VBMI, which Cascade Lake lacks. Without AVX-512 VNNI a served base is multiplied through candle's kernels as before, and on any CPU more threads than cores do not help: a decoded token is bound by memory, and the thread pool stalls when a thread is descheduled.

- **One expert is taught no more than it can learn** ([#452](https://github.com/albedosehen/antumbra/pull/452)). A scope's set holds every behavior its expert already learned, then accepted ones never taught, oldest first, then ones taught before and missed, up to the workspace's `behaviors_per_expert`. A set never drops a behavior its expert learned. The rest wait, accepted, and the server's log says how many when a set is full.
- **A behavior the base model already follows is left out of the set** ([#452](https://github.com/albedosehen/antumbra/pull/452)). By its scope's last training, the base model passed it before any training, so there is nothing to teach, and in a crowded set it is the one the expert ends up worse at than the base: what refused the hundred-behavior set was such a behavior, falling from 0.67 to 0.00.
- **`list_behaviors` says which behaviors wait for room and which the base already follows** ([#452](https://github.com/albedosehen/antumbra/pull/452)), as `waiting_for_room` and `followed_by_base`, always present.

### The console and the dashboard

- **The Training page says how many of a scope's behaviors wait for room, and what the ceiling is**, and the dashboard's Behaviors section tags a behavior that waits and one the base model already follows ([#452](https://github.com/albedosehen/antumbra/pull/452)).

### Known limits

- **A scope stops learning once its expert holds the ceiling.** What it accepts after that waits until a scope can be taught by more than one expert.

### Experts on a machine without a GPU

- **A build with no GPU backend answers from a quantized base** ([#265](https://github.com/albedosehen/antumbra/pull/265)). The server and the CLI built their engines over the dense base, which on a CPU reads about 6 GB a token: about 1.4 tokens a second on an 8-core laptop, after a three-minute load. `antumbra-mcp --serve-quant` (`ANTUMBRA_SERVE_QUANT`) takes `auto` (the default), `off`, `q8_0` or `q4_k`, and the CLI's `ask` and `serve` follow the build the same way. With no GPU backend `auto` is Q8_0, at about six times the dense base's decode speed; a `cuda` or `metal` build stays dense, and `--serve-quant off` restores the dense base anywhere. The server says at start which backend and base form it serves from.
- **Neither quantized form is the dense base, and the difference is measured** ([#317](https://github.com/albedosehen/antumbra/pull/317)). Over 113 held-out examples of two experts, Q8_0 ranks another token first at 3.6% of positions and Q4_K at 14.4%, and 82 and 79 answers pass their behavior's check against the dense base's 85. Q8_0 is the default because it moves an expert least and decodes within 8% of Q4_K. The live checks that measure this (`quant_drift`, `cpu_serve`, `qmatmul_rows`) time the pass over the prompt and each token after it apart: on an 8-core laptop CPU with one expert, Q4_K reads a prompt at 68.8 tokens a second and decodes at 9.0, and Q8_0 at 60.4 and 8.0. They are ignored unless asked for, and no serving or training path changes.
- **What a quantized base does to an expert is recorded on its card** ([#381](https://github.com/albedosehen/antumbra/pull/381)). A training that admits its expert reads the held-out examples through the model as trained and through the base quantized, and writes the comparison under `drift` on the expert's card: how often another token ranks first, and the mean shift. Q8_0 is measured unless `--behave-drift` (`ANTUMBRA_BEHAVE_DRIFT`) on the server or `--drift` on the CLI names other forms; `off` records none. It is recorded and not acted on: nothing reads it to decide where an expert is served.

### Experts on more than one machine

- **A refused retraining no longer replaces the adapter that is served** ([#357](https://github.com/albedosehen/antumbra/pull/357)). Every training of an expert saved its adapter over the one file the admitted expert was served from, before it was known whether the training would be admitted, so after a restart a refused training's weights were the ones loaded. A training now saves a candidate; admission moves it to a file named for its contents, `<expert id>.<sha256>.safetensors`, and records the sha256 and size on the expert's card. The engine loads the file the expert's row names, so an admitted retraining is served without a restart and a refused one is never served. The keeper removes the file an admitted retraining replaced; the CLI's `behave` leaves it and prints where it is.
- **A server serves an expert trained on another machine** ([#365](https://github.com/albedosehen/antumbra/pull/365)). An expert's weights stay on the machine that trained it, so a second server, such as one with no GPU, had its row and could not answer with it. Told where the training server is, `--expert-source http://trainer:8081` (`ANTUMBRA_EXPERT_SOURCE`), a server pulls the adapter the first time it routes to the expert, checks it against the sha256 and size on the expert's row, keeps it under its own adapter directory and serves it from then on without the training server, across restarts. Both servers run with `--http` and the same `--jwt-secret`: each pull is signed for the user being answered and is good for a minute, and the training server gives an adapter only to its owner, or to anyone for a shared expert. A server that verifies with `--jwt-public-key` says at start that the setting is not in effect. An expert admitted before this release has no sha256 on its card and is not pulled until its next admitted retraining.
- **Each admitted adapter has a second copy in copal** ([#382](https://github.com/albedosehen/antumbra/pull/382)). A server that keeps a copal archive (`--copal-addr`) archives every adapter it admits, in the workspace's copal tenant, and puts the file's id on the expert's card. A server that does not hold an expert's adapter looks on its own disk, then asks its expert source, then the archive, and keeps what it reads only if it is the bytes the expert's row names; the server that trained an expert restores its own file the same way when it is gone. A transfer has its own time limit, `ANTUMBRA_COPAL_TRANSFER_TIMEOUT_SECS` (300).
- **Sync carries an expert's row and its status** ([#387](https://github.com/albedosehen/antumbra/pull/387), [#388](https://github.com/albedosehen/antumbra/pull/388), [#396](https://github.com/albedosehen/antumbra/pull/396)). A machine with its own store, kept in step by `antumbra sync`, got its user's memories and behaviors and never learned an expert had been trained from them. An expert's row and each change of its status are now replicated: a retraining and a delete cross as a newer version of one record, a deleted expert's tombstone is purged with the others after the grace period, and an expert demoted or archived on one store is no longer read as active on another. The adapter is a file and is not carried; the row still names the machine that trained it, so a server that reads the row pulls the adapter. Rows written before this release are moved to records of their own the first time an upgraded server or CLI opens the store, and it logs how many it moved. Servers sharing one store should be upgraded together: a server from before this writes rows the old way, and the next start of an upgraded one moves them.
- **A server on an embedded store syncs without being stopped** ([#394](https://github.com/albedosehen/antumbra/pull/394)). An embedded store has one writer, the server that holds it, so `antumbra sync` could not open it while the server ran and the machine stopped serving to sync. Told a remote, `--sync-remote ws://host:8000/rpc` (`ANTUMBRA_SYNC_REMOTE`) with the remote's root user and password (`--sync-remote-user`, and `--sync-remote-pass` or `--sync-remote-pass-file`) or neither for a remote with no authentication, the server runs the same collector on its own connection every `--sync-interval-secs` (15). It holds the store only to read it and to write a batch of rows, never while it waits on the remote, so requests go on being answered, and a row it pulls is written only if nothing newer was written here meanwhile. A remote that is down is tried again and does not stop the server. The stdio server does not sync and refuses the setting.

### Server

- **On an embedded store, a tool call runs as its own caller** ([#319](https://github.com/albedosehen/antumbra/pull/319)). On an embedded store the networked server shares one connection among every identity and signed it in once per request. A `tools/call` sent to `POST /mcp` runs after that request has been answered, so by the time the tool ran the connection could have been signed in again as another identity, and a call could come back with another user's private rows. The connection is now signed in as the session's identity immediately before each tool runs, and the auth lock is held until the tool returns, so tool calls on an embedded store run one at a time. `/mcp/call` was not affected, and a remote deployment, with one connection per identity, is unchanged.
- **The server refuses an HS256 secret under 32 bytes, or the `.env.example` placeholder** ([#334](https://github.com/albedosehen/antumbra/pull/334)). `--jwt-secret` was used as given, so a short secret, or the placeholder anyone can read out of the repository, verified tokens anyone could mint for any workspace and user. `--http` now refuses to start with such a secret and `--mint-token` refuses to sign with one; the message gives `openssl rand -base64 32`. A server running with a secret under 32 bytes needs a longer one before it will start. RS256 (`--jwt-public-key`) is unaffected.
- **The public relic routes have a budget** ([#325](https://github.com/albedosehen/antumbra/pull/325)). `GET /relic/{slug}/public` needs no token and `GET /relic/{slug}/export` reaches the same lookup without one; every call took the server's auth lock, nothing limited how often a client could ask, and `format=pdf` could spend up to a minute of the renderer's time per request. The public lookup now allows each client 30 requests at once and 120 a minute (300 and 3,000 for everyone together), and printing allows 3 at once and 6 a minute per client (20 and 60 for everyone). A request past its budget gets `429` with `Retry-After` before any work. A printed PDF is kept by slug and version (16 entries, up to 8 MiB each), so a repeat request is answered without a second print, and with one connection per identity the lookup no longer takes the lock. Clients are told apart by peer address: behind a proxy that hides it, every client shares one budget.
- **`ingest_document` refuses a document past 512 KiB or 1,024 chunks, before any work** ([#327](https://github.com/albedosehen/antumbra/pull/327)). Neither a document's size nor its chunk count was bounded, and every chunk is embedded one call at a time, so one call under the 4 MiB body limit could mean about 4,200 serial embedder requests. A document past the cap is now refused with `invalid_params` naming the cap, before anything is archived in copal or embedded, and the CLI's `ingest` refuses it the same way. Relics are unaffected.
- **`share_compartment` and `revoke_compartment` act only on a compartment you own, and report what the store did** ([#331](https://github.com/albedosehen/antumbra/pull/331)). `share_compartment` answered `shared: true` whether or not the store kept the grant, so a refused share looked like one that landed; `revoke_compartment` had the same shape. Both now refuse a compartment that is not the caller's, or that does not exist, with `invalid_params` naming `list_compartments`, and a share to the compartment's owner is refused. After the write each tool reads the grant back and reports `internal_error` when the store refused it.
- **A relic's references to private addresses are made inert before it prints** ([#333](https://github.com/albedosehen/antumbra/pull/333)). The PDF renderer (`--pdf-renderer`) fetches whatever a page references while it prints, and the server relied entirely on the renderer being started with `--chromium-deny-private-ips=true`, as the Compose profile does. Before every print the server now replaces with `about:blank` each `http`, `https`, `ws` or `wss` URL whose host is a private, loopback, link-local, shared-range, unspecified or broadcast address, IPv4 or IPv6, or a name that resolves to one. Public hosts and `data:` URIs are untouched. A name that does not resolve stays, and can add up to two seconds to the print.
- **A merge delivery is taken only with a commit sha** ([#335](https://github.com/albedosehen/antumbra/pull/335)). A `pull_request` webhook delivery whose `merge_commit_sha` is not 7 to 40 hexadecimal digits is acknowledged as ignored, with nothing stored or re-anchored. Before, a value with a multi-byte character in its first twelve bytes could panic the delivery handler and drop the ingest. GitHub always sends forty hex digits, so reaching it took the webhook secret or a hostile API answer.
- **A capability card of the wrong shape no longer stops the keeper's behavior training** ([#336](https://github.com/albedosehen/antumbra/pull/336)). An expert whose `capability_card` was an array, a string or a number, or whose `examples` or `audited` section was one, panicked the standing-behavior training task in the keeper and left the audit un-noted. Such a card is now refused with an error naming the expert and left as it was; a null card or a missing section is filled in. It took a hand-edited or legacy row to hit this.
- **One identity and one connection are bounded in what they may hold open** ([#379](https://github.com/albedosehen/antumbra/pull/379)). The networked server bounded the identities it cached but not the sessions one identity could open, and it had no request timeout and no bound on reading a connection's headers. An identity may now hold 16 sessions: opening another is answered `429` with `Retry-After` and a message naming the bound, until one of its sessions is closed with `DELETE /mcp` or goes idle (5 minutes, as before). A request whose response has not begun within 2 minutes is answered `408`, so a `/mcp/call` tool that runs longer is cut while a `GET /mcp` stream is not, and a connection that has not sent its headers within 30 seconds is closed.
- **A token can be revoked by its id** ([#375](https://github.com/albedosehen/antumbra/pull/375)). A token saved on a lost or shared machine stayed valid until it expired, with no way to end it short of rotating the signing key for every workspace. An operator now runs `antumbra revoke-token` with `--token-file` or `--jti`, and within 30 seconds every server refuses that token with the same `401` an expired one gets; a token minted before ids existed carries no `jti`, and the command refuses it and says so. `antumbra setup check` warns when the saved token has three days or less left.
- **The server trusts the network to copal only when told to** ([#366](https://github.com/albedosehen/antumbra/pull/366)). A bare `host:port` in `--copal-addr` became `http://`; it now becomes `https://` unless it names this machine (`localhost` or a loopback address), and an explicit `http://` to any other address is refused at startup unless `--copal-allow-http` (`ANTUMBRA_COPAL_ALLOW_HTTP`, on the CLI too) says the network between the server and the archive is trusted. The networked server (`--http`) also refuses to start when copal's tenancy names the tenant in a request header, unless `--copal-trust-headers` (`ANTUMBRA_COPAL_TRUST_HEADERS`) says the network is the operator's alone; the message names the keyed modes. The compose stack sets both for its own network, and a stdio server, which serves one identity, is not asked for the second.
- **A refusal from an embedder or a reranker carries the endpoint's words** ([#346](https://github.com/albedosehen/antumbra/pull/346)). A 4xx from either became a bare status and the reason was lost: `embed POST {url} failed: http status: 422`. It now reads `embed POST {url} answered 422: input is too long for the model`. A copal answer that succeeds but is not JSON reads `copal POST {url}: the answer was not JSON: …`, where it read `copal response was not JSON: …`; copal's refusal text is unchanged.
- **The server reads `ANTUMBRA_EMBEDDER_MODEL`** ([#341](https://github.com/albedosehen/antumbra/pull/341)). Only the CLI bound `--embedder-model` to that variable, so a server started with it set ignored it. Both binaries now read it (the default stays `all-MiniLM-L6-v2`), and the CLI's `--help` no longer prints the embedder and copal keys when their variables are set.

### The store

- **A grant in another workspace opens nothing in this one** ([#330](https://github.com/albedosehen/antumbra/pull/330)). The read, write and link rules on `memory`, `memory_edge`, `document_chunk` and `grant` looked up a user's compartments without naming the workspace, so a grant row written in another workspace, for the same user and the same compartment key, opened a private compartment here to that user. Writing such a row took the other workspace's owner view or a compartment there with the same key, so it was hard to reach. Every such lookup now names the workspace, and an existing store picks the rules up on connect.
- **Only a compartment's owner can write its row** ([#328](https://github.com/albedosehen/antumbra/pull/328)). The engine's rule let any member of a workspace update or tombstone another member's compartment row, its `owner` included, and a member who rewrote the owner would read everything in the compartment. No tool offered that write. Create, update and delete now require the caller to be the owner; reads stay workspace-wide, and an existing store picks the rule up on connect.
- **A workspace's embedder key is kept to the owner view** ([#329](https://github.com/albedosehen/antumbra/pull/329)). `embedder_config` holds a hosted workspace's embedder endpoint and its bearer key, and any member's session could read the key and rewrite the endpoint. A member session now neither reads nor writes the row. The server and the operator's CLI use it as the owner and are unchanged, and an existing store picks the rule up on connect. The key is also redacted from debug output, so a log line or a panic message cannot carry it.
- **A member can hard-delete only the memories and edges they can write** ([#351](https://github.com/albedosehen/antumbra/pull/351)). The engine's delete rule on `memory` and `memory_edge` checked the workspace alone, so a member session could hard-delete any memory in its workspace, including one in another member's private compartment that it cannot read. No tool reached it: `forget_memory` soft-deletes, and the hard delete and purge paths run in the owner view. Delete now follows the write rules, and an existing store picks them up on its next connect.
- **The record access method is re-asserted on every schema apply** ([#350](https://github.com/albedosehen/antumbra/pull/350)). Table definitions were already rewritten on connect, but the access method was defined only when absent, so a change to its `SIGNIN` clause or session duration reached new stores only and an existing store silently kept the old definition. It is now overwritten like the tables, so a hardened signin or a shorter session reaches every store on its next connect. Principal rows are untouched, and no Antumbra session ends with the re-assert.
- **Distinct workspace and user pairs keep distinct principal records** ([#368](https://github.com/albedosehen/antumbra/pull/368)). A principal's record key was built by joining the workspace and user ids and then replacing `:`, `/`, `\` and `|`, so two different pairs could become one key; the second pair was never provisioned and could not sign in. Each id is now escaped on its own before the two are joined, so no two pairs share a key. No migration is needed: sign-in reads a principal by its `tenant` and `user` fields, so a pair provisioned before the change keeps working. Hosted ids are generated by the server, so reaching this needed caller-chosen ids.
- **Every binary takes the same database flags** ([#340](https://github.com/albedosehen/antumbra/pull/340)). The CLI, the MCP server and the control server each declared the SurrealDB credential flags themselves, and the copies had drifted. All three now read `ANTUMBRA_DB_URL` for the store's address, where only the control server did. The CLI and the MCP server gain the least-privilege `--db-auth database` login (`ANTUMBRA_DB_AUTH`), which needs both a user and a password, and the password no longer prints in `--help` for the CLI and the control server when `ANTUMBRA_DB_PASS` is set.

### The control server

- **The control server refuses to start without a usable mailer** ([#323](https://github.com/albedosehen/antumbra/pull/323)). With `SMTP_HOST` set but SMTP unusable (a bad `SMTP_PORT`, or a binary built without `--features smtp`), it fell back to the stderr mailer and wrote every sign-in link, a live credential for fifteen minutes, to the container's logs. That is now fatal, with a message naming the cause. The stderr mailer is chosen only by the new `--dev-mailer` flag (`ANTUMBRA_DEV_MAILER`), for development; with neither it nor SMTP, startup fails and says what to set. A Compose stack that relied on the implicit dev mailer must set `ANTUMBRA_DEV_MAILER=1` in `docker/.env` or configure `SMTP_*`.
- **Sign-in link requests have a budget per client and for the whole server** ([#332](https://github.com/albedosehen/antumbra/pull/332)). `/login` and `/signup` send an email to any address by design, and the only brake was a cooldown per address as typed: `A@x`, `a@x` and `a+1@x` were three windows, and nothing bounded one client or the server as a whole. The cooldown now treats an address trimmed, lowercased and without its `+tag` as one. In front of it, each client gets 5 requests at once and 10 a minute, and the server 50 at once and 100 a minute; a request past either gets `429` with `Retry-After: 60` before anything is minted or sent. Clients are told apart by peer address, so behind a proxy that does not forward it they share one budget, and each replica keeps its own windows and budgets.
- **Hosted tokens last a week by default** ([#375](https://github.com/albedosehen/antumbra/pull/375)). `--token-ttl-days` defaults to 7 instead of 30, so a token the control server mints expires after a week unless the flag says otherwise.
- **The control server takes its secrets from files, as the MCP server does** ([#359](https://github.com/albedosehen/antumbra/pull/359)). `--db-pass` and `--magic-secret` were flags or environment variables only, so they showed in process listings and shell history. `--magic-secret-file` (`ANTUMBRA_MAGIC_SECRET_FILE`) and `--db-pass-file` (`ANTUMBRA_DB_PASS_FILE`) read the value from a file and trim it; an empty file is refused, and so is giving both a flag and its file. The CLI takes `--db-pass-file` too, `--magic-secret` no longer prints its environment value in `--help`, and `setup hosted` says in `--help` that `--token` and `--signin-link` are for scripts. The file forms are for deployments that mount secrets; the compose stack keeps its `.env`.
- **An invite code is redeemed once, and an account is created once** ([#367](https://github.com/albedosehen/antumbra/pull/367)). Redeeming read the invite and deleted it in a second statement, so two requests racing on one code could both pass, and the second signup silently overwrote the first account's row. The code is now checked and consumed in one statement: a code that is unknown, expired or already used is refused with "invite code unknown, expired, or already used". A second account for the same login is refused with "an account for this login already exists", and the first stands.

### The CLI and the console

- **`antumbra setup hosted` refuses a plain `http://` workspace address unless it is this machine's** ([#326](https://github.com/albedosehen/antumbra/pull/326)). A plain `http://` address was accepted and the token saved for it, so every hook and MCP connection then sent the bearer in cleartext; a sign-in link's scheme was never checked at all. Now `https://` is accepted anywhere, `http://` only for `localhost` or a loopback address, and `http://` elsewhere needs the new `--allow-http` flag. An address with no scheme is refused regardless. The choice is recorded in `setup.json`, and `setup check` lists a cleartext address under things to fix unless it was accepted. Local setups on a loopback address are unaffected.
- **Day-count flags stop at a century** ([#337](https://github.com/albedosehen/antumbra/pull/337)). `antumbra-control-server mint-invite --ttl-days`, `antumbra verifier measure --ttl-days`, `antumbra claude skills --days` and `antumbra claude reanchor --days` take 0 to 36,500. A value past that, or below zero, is a usage error, where a very large one used to panic with a backtrace. `--ttl-days 0` still mints a non-expiring invite.
- **Setup writes the token file whole, into a directory only its owner can enter** ([#371](https://github.com/albedosehen/antumbra/pull/371)). The file was written in place, so a crash mid-write left a truncated token; its directory was made with the process umask rather than 0700; and on Windows the file inherited the directory's ACL. It is now written to a temporary file beside it with mode 0600, synced and renamed into place, its directory is set to 0700 even when it was already there, and on Windows the file gets an owner-only ACL, with a warning from setup where that cannot be set. `antumbra setup check` reports a token file other users can read as a problem; running setup again rewrites it.
- **The CLI and the console report a refused tool call the same way** ([#342](https://github.com/albedosehen/antumbra/pull/342)). Setup, `antumbra claude` and the console each called the server with a client of their own and refused in their own way, so the console showed "answered 400" where the CLI showed what the server said. All three now show the server's own `error` text, read a `401` or `403` as a refused token, and open every message with the tool's name. `antumbra claude` and the console also send the device header, named from `ANTUMBRA_HOST_ID` when it is set and left off otherwise.
- **`--help` describes the capture flags on every command that takes them** ([#354](https://github.com/albedosehen/antumbra/pull/354)). `memory-import`, `consolidate` and `metabolize` share four capture flags with `teach` (`--rounds` and `--lr` among them), but only `teach` described them; all four commands now carry the same lines. The six `antumbra claude` commands word `--surface` and `--token` one way. No flag name, default, environment variable or constraint changed.

### Hooks

- **The bash hooks hand the token to `curl` on stdin, not on its command line** ([#324](https://github.com/albedosehen/antumbra/pull/324)). `antumbra-prompt-recall.sh`, `antumbra-capture.sh` and `antumbra-session-start.sh` passed the `Authorization` header as an argument, where any other user of a shared machine could read it with `ps` for the life of the request. The token now reaches `curl` as a config line on stdin (`--config -`), and the header the server receives is the same. The PowerShell hooks never had the problem and are unchanged.
- **The capture hook names its sentinel safely, in a directory only this user writes** ([#356](https://github.com/albedosehen/antumbra/pull/356)). The sentinel's path was built from the hook's `session_id` and `hook_event_name` as given and kept in the shared temp directory, where another user could create its name first. Both hooks now cut the two values to letters, digits, `_` and `-`, falling back to `default` and `Stop` when nothing is left. The sentinel lives under `$XDG_RUNTIME_DIR` when the session has one, else under `.antumbra/run` in the user's home directory, created with mode 0700; the PowerShell hook uses `%LOCALAPPDATA%\antumbra\run` on Windows.
- **The PowerShell attribution hook denies what the shell hook denies** ([#347](https://github.com/albedosehen/antumbra/pull/347)). `strip-attribution.ps1` had drifted from `strip-attribution.sh`: it let through the robot emoji forms and the bracketed agent name, and worded its deny reason differently. It now denies both and gives the shell hook's reason. The two hooks are held to one list of sixteen cases, eight denied and eight allowed, which CI runs against each.
- **A turn's end is reminded only when a reminder is due** ([#386](https://github.com/albedosehen/antumbra/pull/386)). `antumbra-capture` stopped the first stop of every turn to ask for memories, so a long job that stops many times while it waits was stopped every time. It now lets a stop through when the transcript holds a `store_memory` or `record_behavior` call since it last looked, or when the session was reminded or saved within `ANTUMBRA_CAPTURE_EVERY_SECS` (600; `0` reminds every turn). Under Windows PowerShell 5.1 the hook could not write its sentinel at all, so every stop was reminded, the one after a reminder included; that is fixed. `antumbra setup` gives the hook ten seconds, up from five; an install made before this keeps five until `antumbra setup` is run again.
- **The reminder is feedback, and a compaction is never blocked** ([#392](https://github.com/albedosehen/antumbra/pull/392)). The hook answered with a block, which Claude Code shows its user as "stop hook reported a problem" each time, and before a compaction the same answer blocked the compaction once a session. At a turn's end the reminder now reaches the agent as feedback that keeps the turn going, with no problem reported; before a compaction the hook blocks nothing and tells the summary to keep what has not been stored, and the turn's end after it is reminded. An agent older than Claude Code 2.1.163 does not read the feedback: set `ANTUMBRA_CAPTURE_NUDGE=block` for the old answer.

### Dependencies

- **Both lockfiles are clear of the open advisories, and CI audits both** ([#322](https://github.com/albedosehen/antumbra/pull/322)). rmcp and rmcp-macros move from 3.1.4 to 3.10.0, which bounds the tool schema cache in the Streamable HTTP transport this server runs (RUSTSEC-2026-0461); ammonia moves to 4.2.5 and quinn-udp to 0.5.16. The control server's own lockfile, which the audit job never scanned, takes ammonia 4.2.5, quinn-udp 0.5.16, quinn-proto 0.11.19, rustls 0.23.46, rustls-webpki 0.103.17 and the fixed webpki-roots and webpki-root-certs releases.

### Docs

- **The documented installers name a release and show how to verify the archive first** ([#364](https://github.com/albedosehen/antumbra/pull/364)). The README, `docs/getting-started.md` and `docs/agent-setup.md` installed from `releases/latest`, so the script a reader ran was whatever the latest release held. Every one-liner now names a release tag, and the documents say what the installer checks: it carries the sha256 of every archive it may download and refuses a mismatch before unpacking. The two guides also show the download, `shasum -a 256 -c`, then `tar` form, for a machine that should check the archive itself before anything runs.
- **`docs/security.md` says what holds, what depends on the deployment, and what the operator sets** ([#363](https://github.com/albedosehen/antumbra/pull/363)). The document stated guarantees the code does not provide: that a token's audience is always required, and that no hand-authored SurrealQL exists. It now says a server started without `--jwt-audience` verifies no audience, so the flag belongs wherever two verifiers share a key, and it names the hand-authored statements and states that every caller-supplied value is bound as a variable. A new section lists what holds only where the operator sets it: the audience, HTTPS in front of the networked server, the PDF renderer's `--chromium-deny-private-ips=true`, the control plane's SMTP settings, and the secret files.

### Internal

- **`unwrap` is denied, and `expect` and `panic` are warned, in every crate's production code and tests** ([#339](https://github.com/albedosehen/antumbra/pull/339), [#360](https://github.com/albedosehen/antumbra/pull/360), [#361](https://github.com/albedosehen/antumbra/pull/361), [#362](https://github.com/albedosehen/antumbra/pull/362), [#369](https://github.com/albedosehen/antumbra/pull/369), [#370](https://github.com/albedosehen/antumbra/pull/370), [#372](https://github.com/albedosehen/antumbra/pull/372), [#374](https://github.com/albedosehen/antumbra/pull/374), [#376](https://github.com/albedosehen/antumbra/pull/376)). The workspace lints now hold a rule that was kept by hand, and CI's `-D warnings` makes all three errors. Every test returns `Result` and uses `?`, so a failing fixture reports its error instead of a panic with a backtrace; no assertion or test name changed.
- **Test fixtures come from one module, and two timing-bound tests wait for what they assert** ([#355](https://github.com/albedosehen/antumbra/pull/355), [#377](https://github.com/albedosehen/antumbra/pull/377)). `antumbra_store::testing`, behind the store's `testing` feature, gives `mem_store`, `members` and `signed_in`, and the MCP server's tests have `McpServer::for_tests`. The two MCP HTTP tests that failed on unrelated pull requests and passed on a rerun now wait, bounded, for the span and the `429` they assert.
- **Flags, HTTP clients and small helpers are written once** ([#340](https://github.com/albedosehen/antumbra/pull/340), [#341](https://github.com/albedosehen/antumbra/pull/341), [#342](https://github.com/albedosehen/antumbra/pull/342), [#343](https://github.com/albedosehen/antumbra/pull/343), [#344](https://github.com/albedosehen/antumbra/pull/344), [#345](https://github.com/albedosehen/antumbra/pull/345), [#346](https://github.com/albedosehen/antumbra/pull/346), [#354](https://github.com/albedosehen/antumbra/pull/354)). The database, embedder and copal flags live in `antumbra_store::args`, `antumbra_embed::args` and `antumbra_copal::args` and are flattened into each binary, and each CLI subcommand's clap struct is handed to its command whole. The new `antumbra-http` crate holds the one client for the tool surface and the one `ureq` transport; `antumbra_auth::unverified` reads a token's unverified claims; `antumbra_core::text` and `antumbra_core::stats` hold the character-boundary cut and the mean; and the train crate has one candle error shape and one factor-restore loop.
- **The store names every table once and has one `put` and one `get_row`** ([#348](https://github.com/albedosehen/antumbra/pull/348), [#352](https://github.com/albedosehen/antumbra/pull/352), [#349](https://github.com/albedosehen/antumbra/pull/349)). `antumbra_store::tables` holds a constant per table, used by the schema, the repositories, sync and the control server's contract, so a renamed table is a compile error everywhere it is used; the repositories upsert and read a row through `Store::put` and `Store::get_row`. The control server's nine contract resources state their shared defaults once, through `read_only` and `listing`.
- **Two tests no longer depend on what runs beside them** ([#390](https://github.com/albedosehen/antumbra/pull/390), [#398](https://github.com/albedosehen/antumbra/pull/398)). Two control-server tests shared `ANTUMBRA_DEV_MAILER` through the process environment and one failed now and then; each now holds the variable to itself and puts back what was there. And the server's telemetry tests read their spans at any number of test threads: at four, which is what CI runs, the first of them got no span.
- **Issues and pull requests have forms, and there is a `CONTRIBUTING.md`** ([#318](https://github.com/albedosehen/antumbra/pull/318)). A new issue is a bug, improvement or feature form with a component dropdown; blank issues are off, and security reports go to a private advisory instead of a public issue. `CONTRIBUTING.md` covers branches and PR titles, the release-branch flow, the fmt, clippy and test expectations, and how a release is cut.
- **`antumbra_boundary::find_scope` returns an error for a failing context that is not a JSON object**, where it used to panic ([#338](https://github.com/albedosehen/antumbra/pull/338)). Its one caller today is a test, so nothing changes for a running server.

### Known limits

- Only a standing expert carries the sha256 of its adapter, so only standing experts are pulled, archived and served on a second machine. One admitted before this release gets its sha256, and its copy in copal, at its next admitted retraining.
- Serving an expert on a second machine is new. The pull and the archive are tested against a source and an archive stood up inside the tests; they have not yet been run between two machines or against a deployed copal. Sync was run against a networked SurrealDB 3.3, experts' rows and status included.
- A sync that signs in as a user, and not as the owner, does not carry experts or their status: only an owner connection writes those tables, and such a pass counts each one as refused.
- An adapter is held whole in memory on both machines while it is pulled, and pulls run one at a time.

## 0.2.6 - 2026-11-01

Training you can watch, and experts on the CPU. A standing expert's training now shows in the console as a shadow, and what it missed as a boundary, each read by the scope it trained; a node without a GPU can serve experts at a usable speed; and the memory counts from 0.2.5 add up. x86-64 builds now need a CPU with AVX2.

### Training

- **A standing expert's training is a shadow** ([#256](https://github.com/albedosehen/antumbra/pull/256)). The server's keeper writes it as `exploring` while it trains, then `graduated` when the expert is admitted or `pruned` when it is refused or fails, with a reward curve from the base model's held-out pass rate to the trained one's. The console's penumbra had stayed empty on a server, because only the CLI's loop wrote shadows. An expert minted before this gets its shadow once, from its card.
- **What a training missed is a boundary** ([#256](https://github.com/albedosehen/antumbra/pull/256)). Each behavior the expert did not follow becomes an open boundary beside it, holding the rule, the task it missed and its answer, at the share of that behavior's tasks it failed. Open boundaries are recorded, never gating routing. One goes away when an admitted expert learns the behavior or the behavior is no longer taught.
- **A boundary can belong to a user** ([#256](https://github.com/albedosehen/antumbra/pull/256)). One from a behavior holds that user's own rule, so only they read it. Existing boundaries have no owner and stay shared.

### The console

- **A training reads by its scope** ([#259](https://github.com/albedosehen/antumbra/pull/259)). The penumbra listed a standing expert's training by its id, some sixty characters with the scope where the list cut it off; it now reads `✦ code · behaviors · 0.42 → 0.91`, the pass rate from the base model's to the trained expert's, and its panel gives both. Every shadow's row now ends in where its reward went, its status in its glyph and color.
- **An open boundary shows what it was recorded from** ([#259](https://github.com/albedosehen/antumbra/pull/259)): the scope, the task the expert missed and its answer, and whose it is. The inspector showed a boundary's context only when it was actionable, and every boundary a training leaves is open. The gate summary lists only actionable boundaries, the ones that inhibit routing.
- **Prune and graduate leave a training to its keeper** ([#259](https://github.com/albedosehen/antumbra/pull/259)). They set a shadow's status for the generational loop to read back; the keeper settles its own trainings and never does, so on one of its shadows the console declines them and says to freeze the expert instead.

### Serving on the CPU

- **A bf16 expert loads into a CPU model** ([#252](https://github.com/albedosehen/antumbra/pull/252)). Experts are saved in bf16 and every CPU model is held in f32, so serving one, or warm-starting from one, failed on the CPU. Each factor is now cast losslessly as it loads.
- **The base can be served quantized** ([#252](https://github.com/albedosehen/antumbra/pull/252)), as Q8_0 or Q4_K, each projection quantized as its layer loads and never dequantized. Experts stay dense beside it. - **x86-64 builds target x86-64-v3** ([#252](https://github.com/albedosehen/antumbra/pull/252)), so candle's quantized kernels use AVX2 instead of their scalar fallback. The release binaries and images need AVX2, FMA and F16C: Intel since Haswell (2013), AMD since Excavator (2015). ARM builds are unchanged.

### Memory

- **Pass-overs add up** ([#255](https://github.com/albedosehen/antumbra/pull/255)). A memory an agent recalled for itself and then drew on counted as used but not as judged, so `judged - used` undercounted the pass-overs of any memory that also had one. Every use now counts as a judgment.
- **The capture hook names the machine** ([#255](https://github.com/albedosehen/antumbra/pull/255)), as the MCP client does (`X-Antumbra-Host` from `ANTUMBRA_HOST_ID`), so what an agent recalled for itself is judged against the turn that used it. Run `antumbra setup` again, or copy the new `antumbra-capture` over a hand-installed one.

### Docs

- **How Antumbra holds models** ([#257](https://github.com/albedosehen/antumbra/pull/257)). The docs said GGUF and NF4, which the code never used. They now say what it does: a safetensors base from the Hugging Face hub and safetensors experts, served by candle, trained over a bf16 base (or Q4_K in memory with `--quantize-base`).

## 0.2.5 - 2026-10-29

Memories the system keeps itself. Nobody has to reinforce or penalize a memory: the server counts what recall shows, judges at the end of each turn which of those the answer drew on, links a new memory to what it restates, and lets an unused one fade at its network's half-life. An operator steers it with knobs while it runs ([#253](https://github.com/albedosehen/antumbra/pull/253)).

### Memory

- **The system watches how each memory is used.** Recall counts every memory it returns; the prompt hook names its session, and the capture hook reports the end of each turn (`observe_turn`, which no agent is offered). The server asks the relevance head whether the answer drew on each memory the session was shown, or compares embeddings where no head is configured: drawn on counts as used, the rest as passed over. What an agent recalled for itself counts only when the answer drew on it.
- **Strength.** Each memory's strength is its confidence, halved for every half-life since it was last of use and lowered the more often it was passed over. It is read at every recall, never stored. Recall returns it as `strength` and lets it move the order a little after relevance, within each scope.
- **New memories link to what they restate.** `store_memory` links a new memory (`references`) to the existing ones it comes close to, and one close enough counts as that memory recurring. It returns the ids it linked.
- **An agent's own judgment still counts.** `reinforce_memory` and `penalize_memory` are an agent's lever when its work shows a memory right or wrong; the prompt hook now shows each memory's id so it can.
- **The counts live apart from the memory** (`memory_use`), so counting a recall never re-sends a memory to other devices. Each server counts what it sees.
- **`relate_memories` refuses an end that does not exist** instead of storing an edge to nothing.

### The console

- **Knobs (`K`).** The workspace's memory knobs: whether the system governs memories, the half-life of an unused fact, experience, judgment and volatile memory, how sure it must be that an answer drew on a memory, how close a new memory must come to be linked or to count as a restatement, the most links, how much a pass-over weighs, and how far strength moves recall. Anyone sees them; an operator's token turns them, and they apply to the next recall.
- **The Memory page shows strength** beside confidence, how often each memory was recalled, used and passed over, and when it was last of use. It lists each network strongest first and leaves out edges whose end is gone.

### Hooks

- Run `antumbra setup` again to install the new hooks. A hook installed by hand needs the new `antumbra-prompt-recall` and `antumbra-capture` copied over it.

- Behaviors are recorded with at least four examples, so training can hold one in four out and admit a standing expert by it. A scope's standing expert is admitted for the behaviors it learned, instead of being refused when any one is missed. A refused set stays refused across restarts and says why ([#204](https://github.com/albedosehen/antumbra/pull/204), [#205](https://github.com/albedosehen/antumbra/pull/205), [#206](https://github.com/albedosehen/antumbra/pull/206)).

### Docker

- Two opt-in Compose profiles: `copal`, which keeps each ingested document's original, and `telemetry`, an OpenTelemetry Collector that reports the host, containers, SurrealDB, GPU and reranker to the same endpoint as the server's traces ([#199](https://github.com/albedosehen/antumbra/pull/199), [#202](https://github.com/albedosehen/antumbra/pull/202)).
- The control server's `contract` feature takes `oneiriq-kayak` from crates.io, so building it needs no access to a private repository ([#200](https://github.com/albedosehen/antumbra/pull/200)).

## 0.1.0 - 2026-10-07

The first public release. Antumbra plugs into the coding agent you already use and gives it a memory that carries across sessions and machines, along with where each memory came from. Claude Code is the agent it is tested with; any MCP client can use its tools over stdio or HTTP.

### Setting it up

Install the CLI with the installer for your OS (below), then, with Docker and ollama running, set it up from a clone of this repository, which the local stack is built from:

```sh
git clone https://github.com/albedosehen/antumbra.git
cd antumbra
antumbra setup local
```

Connecting to a hosted workspace needs no clone: `antumbra setup hosted <url> --token-file <file>`. Then `antumbra setup check` confirms every piece. [docs/getting-started.md](https://github.com/albedosehen/antumbra/blob/main/docs/getting-started.md) walks through it, and [docs/agent-setup.md](https://github.com/albedosehen/antumbra/blob/main/docs/agent-setup.md) lets your agent do it for you.

### What's in it

- **One-command setup.** `antumbra setup local` checks Docker and ollama (and, on macOS and Linux, `jq` and `curl`), pulls the embedding model, generates the stack's secrets, starts SurrealDB and the server, mints a token, proves recall works with it, and connects Claude Code: the hooks, the MCP server and the settings, backed up and only added to. Running it again keeps what is already in place.
- **Hooks for Claude Code.** Recall at the start of each session and with each prompt, and a nudge to write back what was verified when a session stops.
- **Memory with provenance.** A memory about code carries the repository, commit and branch it was learned at. Recall scopes to where you are and marks each memory as live, not on HEAD, or orphaned, and a merged branch's memories move to its merge commit.
- **Recall** that fuses dense and full-text search by rank, with an optional cross-encoder rerank whose calibrated floor lets it answer "nothing relevant". Its legs rank keys instead of reading rows, and memory's read rule reads the owner's compartment record directly, one key read per row instead of a subquery ([#196](https://github.com/albedosehen/antumbra/pull/196), [#198](https://github.com/albedosehen/antumbra/pull/198)).
- **Handoffs** between your machines, a **dependency graph** with `blast_radius`, **compartments** you share on purpose, **documents** recalled separately from memory, and **behaviors**: rules you record with a check that has to tell examples from violations.
- **The operator console** (`antumbra-tui`) and a read-only web dashboard at `/dashboard`.
- **Experts (experimental).** Training and serving small LoRA experts needs an NVIDIA GPU and a source build with the `models` feature. The prebuilt binaries are the light, no-GPU build.

### Known limits

- Setup does not start the reranker. Recall works without it but cannot say "nothing relevant", and on a CPU the reranker is too slow to sit in front of every prompt.
- The server advertises all 33 MCP tools. The 17-tool `agent` profile is a server setting (`ANTUMBRA_TOOLS=agent`) that setup does not apply yet.
- Claude Code is the only agent tested so far.
